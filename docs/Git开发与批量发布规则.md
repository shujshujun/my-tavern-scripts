# 《人妻公寓》Git开发与批量发布规则

更新日期：2026-09-04

## 一、采用的模式

本项目采用：

> **多个相关BUG或单个完整功能形成一个本地任务提交；多个任务提交累计到下一版本；用户明确要求发布时，才统一正式构建、组卡、打标签和推送。**

本地 `commit` 只是开发检查点，不等于发布。一个正式版本可以包含多条 `fix`、`feat`、`test`、`docs` 和素材接线提交。

历史交接文档或旧模板中的笼统“禁止commit”属于旧工作方式，不能反向覆盖本规则。只有用户当前明确要求“不要提交”、任务本身是只读审查／未完成试验，或当前文件存在无法分离的混合所有权时，才继续禁止该任务提交。

## 二、分支与工作区

1. 已发布分支／标签只代表外部版本，不再作为长期并行施工现场。
2. 当前混合脏工作树完成一次专门收口后，日常整合分支统一使用 `develop/rq-next`；下一版本号确定后可以改名，但不得提前创建发布标签。
3. **只有一个写入任务时**，可以直接在下一版本整合工作区顺序开发。
4. **两个及以上窗口可能同时写文件时**，每个写入任务必须使用独立 worktree 和任务分支，例如 `task/201-divorce`、`task/302-post-ending`、`task/mobile-fixes`。共享 checkout 只允许一个写入者；其他窗口只能只读审查。
5. 只读审查、讨论和问题登记不需要创建分支或提交。
6. 不得用 `reset`、`restore`、`checkout`、`stash`、`clean` 或删除 untracked 文件来解决并行冲突。冲突必须通过读取当前双方改动、语义合并和重新验证处理。

## 三、任务提交的粒度

1. 一个提交对应一个能够独立说明、独立验证、独立回退的任务单元。
2. 同一机制的一组相关BUG可以合并为一个 `fix` 提交；同一功能的源码、专项测试和必要文档可以形成一个完整 `feat` 提交。
3. 不相关的角色线、手机系统、数据库、素材生产和发布修改不得塞进同一个提交。
4. 长任务可以按稳定里程碑提交，例如“状态机与测试完成”“CG路由与清单完成”；未审核候选、诊断试验和半成品不得冒充完成提交。
5. 纯讨论、未落地设计、只读审查以及验证失败的实现默认不提交。

## 四、什么时候允许本地 commit

实现任务同时满足以下条件后，主代理／任务所有者默认可以创建本地任务提交，无需等到正式发布：

1. 当前任务边界和改动文件已经明确；
2. 已读取每个目标文件的当前内容及当前 diff；
3. 专项测试通过；
4. 相关回归与定向类型／静态检查通过，或已有失败被证明为任务开始前存在且已如实记录；
5. 需要隔离生产构建的功能已完成隔离构建，且正式 `dist/**` 前后不变；
6. 已复核实际 diff，确认没有混入其他窗口内容；
7. 用户没有明确要求“只审查”“不要修改”或“不要提交”。

任务没有满足上述条件时，不得为了让工作树看起来干净而提交。

## 五、提交安全门

1. 只能显式暂存本任务文件：

   ```bash
   git add -- path/to/file1 path/to/file2
   ```

2. 严禁使用：

   ```bash
   git add -A
   git add .
   git commit -am
   ```

3. 提交前必须检查：

   ```bash
   git diff --cached --stat
   git diff --cached
   ```

4. 目标文件若同时含有其他窗口尚未完成的改动，不能整文件暂存；应停止提交该文件，登记混合所有权，交由整合窗口处理。不得用覆盖、回退或格式化把别人的改动消掉。
5. 提交信息使用清楚的任务语义，例如：

   ```text
   fix(手机): 修复刷新后微信上下文回退
   feat(201): 完成许曼君分居四幕流程
   test(302): 补齐共居失败与回档边界
   assets(201): 接入离婚结局CG清单
   ```

6. 默认不 `amend`、不 `rebase`、不改写既有提交历史；确需整理时由整合任务专门执行。

## 六、任务分支如何进入下一版本

1. 独立 worktree 完成并产生本地任务提交后，由整合窗口复核并合并或 cherry-pick 到 `develop/rq-next`。
2. 合并前重新读取整合分支当前文件，检查共享状态机、Schema、手机入口、资源清单和测试是否冲突。
3. 合并冲突不得机械选择 ours／theirs；必须按功能语义保留双方有效改动并重新跑相关测试。
4. 整合完成只代表进入下一版本候选，不代表已经发布。

## 七、正式发布门

只有用户明确说“发布”“正式构建并组卡”或给出等价授权时，才允许：

1. 冻结下一版本整合分支；
2. 更新版本号、资源标签和发布说明；
3. 运行正式生产构建并写入 `dist/**`；
4. 组卡并核验JSON／PNG内嵌数据；
5. 创建发布 commit、版本 tag；
6. push到远程仓库或素材仓。

没有发布授权时，任务提交可以存在于本地，但禁止正式构建、组卡、tag 和 push。

## 八、当前超级脏工作树的过渡规则

当前 `release/rq0904` checkout 已混有多个窗口长期累积的 tracked 修改和大量 untracked 文件。本规则不授权对这些历史内容执行批量暂存或一次性盲提交。

在专门的“当前工作树收口”任务完成以前：

1. 禁止 `git add -A`、`git add .`、批量删除、清理或回退；
2. 共享 checkout 同一时间只允许一个写入窗口；
3. 新任务只有在其文件所有权完全明确、实际 diff 已逐项复核时，才可以提交自己的明确文件；
4. 任何含混合改动的文件继续保持未提交，并登记给后续整合；
5. 并行写入任务若依赖当前未提交成果，应先完成安全收口检查点，再创建独立 worktree，不能从旧HEAD直接开工后假装已包含当前成果。

专门收口时应先暂停其他写入窗口，分类产品源码、测试、设计文档、正式素材、制作中间物和临时文件，再用显式文件清单建立本地安全检查点；该检查点仍不是正式发布。
