## 十一、如何区分回归、冲突和旧BUG

每个问题必须归入下列一种：

- `POST-0904-REGRESSION`：`f1bbde58`正常，当前工作树被新修改破坏；
- `NEW-FEATURE-BUG`：新功能自身流程错误；
- `CROSS-FEATURE-CONFLICT`：两个新功能或新旧功能抢同一资源／状态；
- `INCOMPLETE-WIRING`：有设计、状态或测试，但生产入口／消费者／素材未接通；
- `OUTDATED-TEST`：生产行为合理改变，旧断言未更新；必须先证明新行为正确，不能先贴标签；
- `LEGACY-BUG`：`f1bbde58`基线已存在的真实BUG；
- `ENVIRONMENT-BLOCKER`：由当前并行未完成文件、依赖或工具导致，且不是被审功能本身；
- `DESIGN-CONFLICT`：两份当前设计或代码行为互相矛盾，需要用户决策。

判断是否为旧BUG时，必须读取基线同一路径，并尽量用基线测试或最小只读复现证明，不能凭文件修改日期猜测。

## 十二、源码追踪方法

### 12.1 修改过的旧文件

对每个共享旧文件：

1. 完整读取当前文件；
2. 查看该文件当前diff；
3. 用 `git show f1bbde58:路径`读取基线；
4. 将每个hunk归入一个功能族；
5. 搜索该hunk涉及符号的全部当前生产者和消费者；
6. 搜索基线中同符号的生产者和消费者；
7. 判断新增行为是扩展、替换、旁路还是破坏旧不变量。

推荐：

```bash
git -c core.quotepath=false diff --unified=80 f1bbde58 -- 路径
git grep -n '符号' f1bbde58 -- src/人妻公寓 tests/人妻公寓
grep -RIn --include='*.ts' --include='*.vue' --include='*.mjs' '符号' src/人妻公寓 tests/人妻公寓
```

### 12.2 未跟踪新文件

未跟踪文件不会出现在普通 `git diff` 中。必须：

1. 完整读取；
2. 搜索谁import它；
3. 搜索它import谁；
4. 搜索所有导出是否有生产消费者；
5. 搜索其中新增状态路径、事件、完成ID、道具ID、消息键和素材键；
6. 检查是否只被测试引用、却没有生产接线；
7. 检查生产文件是否import了未跟踪模块，导致发布时漏文件即构建失败。

### 12.3 必做全局矩阵

至少生成并人工审查：

- `eventOn`／`eventEmit`／`eventClearEvent`矩阵；
