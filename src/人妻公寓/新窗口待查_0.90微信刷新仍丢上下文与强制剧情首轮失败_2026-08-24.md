## 二、W-001：v0.90 刷新后微信上下文仍丢失

### 2.1 最新生产证据

用户在 2026-08-24 明确纠正：**正式 v0.90 玩家仍然反馈刷新后微信上下文和记录丢失**。

因此此前“0.90 已彻底解决普通网页刷新，只剩真实 swipe 并发竞态”的结论撤回。自动化通过不能推翻生产复现。

### 2.2 v0.90 确实包含的修复

`rq0.90` 已包含：

- `手机时间线租约.ts` 的字段级锚签名比较；
- 忽略正文位 `[1] mes` 的同分支变化；
- `swipe_id` 的 `undefined/null → 0` 归一；
- 其余字段仍严格比较；未知签名形状失败关闭。

对应文件：

- `src/人妻公寓/脚本/游戏逻辑/手机时间线租约.ts`
- `tests/人妻公寓/手机同楼分支隔离.test.mjs`
- `src/人妻公寓/新窗口交接_微信刷新上下文丢失根因与修复_2026-08-23.md`

旧交接第 62—64 行曾正确指出 v0.86 只修 `swipe_id`、v0.90 再补 `mes`；但第 269—271 行“只放宽 mes 已充分”的结论现在已被正式 v0.90 玩家复现否定。

### 2.3 v0.90 后已有但尚未发布的本地修复

当前脏工作树在 `手机/数据层.ts` 给唯一增量写入口增加了 `时间线切换协调中()` 双重门，防止：

```text
真实 swipe／删楼事件已上锁
→ 新微信消息抢先写入
→ 随后的同楼裁枝把新消息也删掉
```

该补丁只在明确的 swipe／删楼协调期间生效。普通网页刷新不进入这把锁，**不能解释为已修当前生产问题**。

### 2.4 已由源码确认的剩余结构风险

#### 风险 A：分支签名仍严格依赖宿主可变字段

当前签名字段为：

```text
[is_user, mes, send_date, swipe_id, name, force_avatar]
```

v0.90 只容忍 `mes`，仍严格比较 `send_date/name/force_avatar`。不同 SillyTavern／酒馆助手版本、角色卡更新、身份或头像归一、旧消息补字段，都可能让同一真实分支在刷新后失配。

目前尚无该名 v0.90 玩家的刷新前后原始锚字段，**不能先猜具体是哪一格变化**。

#### 风险 B：普通增量写把过滤后的投影视为原始库

`手机/数据层.ts` 的 `写库增量` 当前执行：

```text
读取原始 _微信
→ 筛当前手机时间线（楼／时／分支）
→ 得到“新鲜”可见投影
→ 合并本次消息／已读／节拍
→ 用投影整份覆盖 _微信
```

关键位置（当前工作树行号可能继续漂移）：

- 约 `629—630`：从原始消息、朋友圈构造过滤投影；
- 约 `686`：`_.set(vars, '_微信', 新鲜)` 整份覆盖。

影响链：

```text
刷新期间任一锚字段临时失配
→ 读库先把旧记录隐藏
→ 自动通知、实时已读或下一条消息触发普通增量写
→ 过滤投影不含旧记录
→ 投影覆盖原始 _微信
→ 临时不可见升级为永久数据删除
→ 私聊气泡、微信摘要、最近本人私聊和稳定事件键同时丢失
```

`压缩微信会话记录` 也从过滤后的 `原消息` 开始，在有变化时回写 `v.消息`，必须纳入同族审查。

#### 风险 C：聊天变量／硬保存真实就绪仍需重新复核

v0.86 已增加：

- `手机楼轴已就绪()`；
- `立即持久保存手机聊天变量()`；
- 事务边界 `saveMetadata/saveChat`。

旧排查曾以本机新版 SillyTavern 和早期短档排除冷启动与落盘。但新生产复现可能来自不同宿主／插件版本；必须重新核对：

- `SillyTavern.chat` 就绪时，`getVariables({type:'chat'})._微信` 是否也已经真实恢复；
- 宿主是否暴露可等待的 `saveMetadata/saveChat`；
- 玩家看到消息后到刷新前，硬保存是否实际成功；
- 所有 `写库增量` 调用者是否都在玩家可见事务边界等待硬保存。

### 2.5 五问

1. **设计初衷**：微信既是独立聊天，也是正文、楼务、孕产、回档和分支的投影；刷新必须保留当前分支记录，真实 swipe／删楼又必须裁掉旧分支。
2. **正常运行**：普通刷新、宏展开、思维链剥离、卡片升级和展示字段归一不改变分支；只有明确 swipe、删楼、回档、切聊天才改变归属。
3. **游戏影响**：记录消失会同时打掉最近私聊、摘要、楼务稳定键和角色短期上下文，造成角色失忆及重复派发。
4. **BUG 原因**：具体首个失配字段待玩家证据确认；但“过滤投影覆盖原始库”已由源码确认，会把任何瞬态误判放大成永久删除。
5. **兼容边界**：修复不得复活真实旧分支，不得破坏回档裁剪、稳定键幂等、已读顺序和旧 v7/v8/v9 存档。

### 2.6 实机复测仍建议取得的证据

优先索取玩家刷新前后的聊天导出／控制台诊断；诊断不得输出完整私聊正文，只需：

- 原始 `_微信.消息`／`圈` 数量；
- `读库()` 后可见数量；
- 首个失配记录的 `楼`；
- 持久签名与当前消息六字段逐位“相等／不等”结果；
- `手机楼轴已就绪`、末楼、当前绝对时段、聊天 ID；
- 最近一次手机硬保存结果与宿主方法名。

最小复现矩阵：

1. 新档普通刷新；
2. 旧档升级到 0.90 后刷新；
3. 开局楼含宏；
4. 开启思维链后刷新；
5. 更新角色卡／角色头像后刷新；
6. 不发生任何新写时刷新；
7. 刷新后触发实时已读／自动通知／新私聊，再检查原始库是否被物理缩短；
8. 真实 swipe、删楼、回档反例仍必须裁枝。

### 2.7 修复前待证方案（现已由第六节收敛）

当前只允许把以下方向作为待证方案：

- 普通读写只生成当前分支投影，不得顺手物理删除暂时不匹配记录；
- 只有明确 swipe／删楼／回档事务拥有物理裁枝权；
- 用持久稳定的消息／分支令牌替代正文、名称、头像等展示字段，或建立可验证的旧锚兼容层；
- 增加聊天变量就绪门与非敏感诊断日志；
- 旧档自愈必须先证明不会复活真实旧分支。

未经玩家现场字段和行为测试，不得直接“忽略所有签名字段”或全局保留全部分支。

## 三、S-001：强制剧情第一次生成失败，第二次成功

### 3.1 玩家现象

玩家反馈：每次出现强制剧情，第一次 AI 生成肯定失败，需要点击再次生成，第二次才正常。

尚缺：第一次失败时最终 toast／控制台错误原文。必须区分：

- **启动前忙门**：没有真实调用正文 AI；
- **正文生成后提交失败**：AI 正文已经返回，但事务／转正／票据提交失败。

### 3.2 与源码吻合的高概率竞态

上一回合成功后：

1. `回合引擎.ts` 广播 `人妻公寓:回合完成`；
2. 游戏逻辑监听启动 `手机节拍()`；
3. 回合引擎安排数据库骨架／增量更新后台任务；
4. App 拉取新状态，发现同场强制剧情票，下一任务拍发送 `人妻公寓:检查场景剧情`；
5. 到场激活／重试入口检测到数据库 AI、手机节拍或手机 AI 仍忙，立即返回；
6. 后台任务结束后，玩家再次点击，同一剧情成功。

关键位置：

- `回合引擎.ts` 约 `3007`：广播回合完成；
- `回合引擎.ts` 约 `3020`：安排数据库回合后处理；
- `index.ts` 约 `3287—3299`：回合完成后启动手机节拍；
- `App.vue` 约 `5096—5104`：同场后续剧情下一帧检查；
- `index.ts` 约 `2106—2115`：到场剧情遇后台忙直接返回；
- `index.ts` 约 `1430—1437`：开始／重试剧情遇后台忙直接失败；
- `回合引擎.ts` 约 `2026—2048`：执行回合再次检查数据库／手机生成占用。

这不是“AI 第一遍不会写”，而是强制剧情与可选后台生成缺少统一优先级／等待交接。

### 3.3 为什么现有测试全部通过仍会漏

当前相关测试 41／41 通过，分别证明：

- 强制剧情有持久票、失败后可重试；
- 手机／数据库／正文不能并发；
- 强剧情期间手机只读；
- 到场票按下一帧检查；
- 后台忙时失败关闭。

但没有组合测试：

```text
一个成功回合同时产生同场强制剧情
＋ 同一回合完成事件启动手机节拍
＋ 数据库后台整理已经排队
→ 强制剧情应优先一次启动或自动等待，而不是制造一次玩家可见失败
```

### 3.4 五问

1. **设计初衷**：强制剧情是不能丢失的确定性票；只有正文成功落地才消费。手机和数据库后台记忆属于较低优先级或可选副作用。
2. **正常运行**：到达目标地点后，系统应先取得前台生成所有权；后台未释放时自动等待／顺延，不能要求玩家用第二次点击完成正常流程。
3. **游戏影响**：每次强剧情固定失败一次，浪费等待时间，误导玩家认为模型或剧情损坏，也掩盖真正 API 失败。
4. **BUG 原因**：回合完成后的三类任务并发抢同一生成通道；互斥门只会拒绝，没有强剧情优先级或自动交接。
5. **兼容边界**：不得因此允许真实并发生成；不得提前消费剧情票；失败、取消、超时、swipe、回档和切聊天仍必须保持原事务语义。

### 3.5 实机复测验证顺序

先取得玩家第一次失败的最后提示。按文本分流：

- `AI通道仍在处理其他内容`／`手机后台消息正在生成`／`数据库AI仍在结算`：验证启动抢占链；
- `场景剧情请求世代已经变化`／`队首已经变化`：验证票据与请求世代；
- `转正失败`／`正文不完整`：验证临时楼、预设输出与持久转正；
- 正文已经显示后才失败：必须检查最终提交和回滚，不得按忙门修复。

复现矩阵：

1. 数据库已安装／未安装；
2. 本拍手机有内容／无内容；
3. 同场等待票自动触发／玩家手动点击开始；
4. 即时业务直接建活动票／远处票到场激活；
5. 连续两张同场强制剧情；
6. API 真失败、取消、超时；
7. swipe、删楼、回档、切聊天；
8. 第一次失败后确认业务奖励、道具、冷却不重复提交。

### 3.6 修复前待证方向（现已由第六节收敛）

待验证方案：

- 同场强制剧情票在 `回合完成` 时优先于可选手机 AI 和数据库 AI；
- 后台任务已开始时，剧情入口等待有界释放并自动续发，而不是广播假失败；
- 数据库后台任务发现新前台剧情已开始时安全让路，下一个成功楼再补；
- 保留统一互斥租约，绝不能用删除忙门的方式允许双 AI 并发。

## 六、2026-08-24 本窗口落地记录

### W-001

- `手机时间线租约.ts`：持久记录只以 `is_user` 角色侧与归一后的 `swipe_id` 识别分支；正文、发送时间、显示名和头像仍保留在六字段签名里供在途租约严格作废，但不再作为刷新后的持久读库硬门。旧助手楼 `is_user=null/undefined` 与刷新后的 `false` 兼容。
- `手机/原始库投影.ts`、`手机/数据层.ts`：普通增量和摘要压缩只更新当前可见投影，再合回原始消息／朋友圈；暂时失配、其他分支或未来楼记录不会再被普通写入物理删除，单调序从完整原始库最大安全序继续。
- `手机分支隔离.ts`、`index.ts`：明确 `MESSAGE_DELETED` 按删除楼及后续楼物理裁枝；真实 swipe 继续裁同楼旧分支，回档继续使用既有楼／时轴事务。由此放宽刷新软字段时仍保留真实分支隔离。

### S-001

- `场景剧情事务.ts` 新增统一前台所有权判定：普通活动票、同场等待票、未知旧档票、专用特殊场景和荣耀洞优先；远处等待票不阻塞日常后台。
- 手机总节拍、独立冷落预警和数据库回合后处理复用同一判定。数据库硬骨架仍先落库，但在触发可选数据库 AI 前重读最新场景状态并让路；下一个成功正文继续补 pending 骨架。
- 生成互斥、失败保票、请求世代、取消、swipe、回档、切聊天和成功后消费时机均未放宽。
