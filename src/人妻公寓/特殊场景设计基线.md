# 人妻公寓：特殊场景设计基线

> 记录日期：2026-07-30
>
> 状态：通用运行框架已拍板；九种场景的逐轮玩法、轮数和节拍内容待下一步逐项讨论。
>
> 本文取代当前源码中“购买即扣款、立即排队一次性事件、立即结算”的旧设计口径。

## 一、定位

特殊场景是玩家满足长期前置后购买并主动开启的多轮奖励剧情，不是一件“买下立即生效”的消耗品，也不能压缩成一个 AI 回合。

通用框架参考云霜凝场景引擎的以下原则：

- 单一“进行中特殊场景”状态机；
- 场景期间锁定参与者和发生地点；
- 每个成功生成的 AI 回合只推进一个剧情节拍；
- 最终轮成功落地后才登记完成并结算；
- 同楼重掷重放当前节拍，生成失败不推进。

不照搬云霜凝按聊天楼层推算轮次和最终正文生成前提前清场的实现。人妻公寓以“AI 正文成功落地”作为推进和最终结算凭据。

## 二、商店可见性

特殊场景页签解锁后，九种特殊场景全部可见，不因具体前置未满足而从货架消失。

每项场景有三种显示状态：

1. **锁定**：显示名称、描述、价格和未满足条件，不可购买；
2. **可购买**：全部购买前置满足，可购买进入背包；
3. **已完成**：显示已经历状态，不可再次购买。

锁定条目必须让玩家知道缺少什么，例如：

- 指定角色尚未达到要求阶段；
- 缺少指定常驻道具；
- 丈夫路线尚未开启；
- 母亲尚未入列；
- 其他参与人数不足。

“未知条件”只可用于确实需要保密的剧情谜底，不能把整个场景隐藏。

## 三、购买与背包

购买特殊场景票时只做以下事情：

- 复核货架开放和购买前置；
- 扣除现金；
- 将场景票放入背包。

购买时严禁：

- 立即触发剧情；
- 写入待发送剧情事件；
- 增加任何角色数值；
- 修改欠租、丈夫路线、朋友圈等世界状态；
- 登记场景完成。

同一种一次性场景票在背包中、进行中或已完成时均不可重复购买。

## 四、启动方式

默认情况下，玩家必须移动到符合条件的参与妻子所在位置，当面赠送背包中的特殊场景票，才能尝试启动。

启动时脚本必须再次复核：

- 场景票确实在背包；
- 没有其他特殊场景正在进行；
- 当前地点存在可接收该场景票的目标妻子；
- 所有角色、道具、阶段和丈夫路线前置仍然成立；
- 动态选出的参与人数仍满足要求。

复核失败时不消耗场景票，也不启动剧情。

多人场景可以向任一名符合该场景启动资格的参与妻子赠送。启动成功后，脚本一次性确定本次场景的完整参与名单；后续不得因户列表顺序、角色日常位置或阶段变化重新抽取参与者。

允许单个场景声明明确的启动特例。例如「录像带」的演员与控制地点固定，只能由玩家在管理员室直接使用场景票，不需要再次赠送给角色。特例必须写入场景配置，不能由前端凭名称硬编码。

## 五、多人集合与头像显示

启动多人特殊场景时，其他符合条件的参与者在叙事层被集合到玩家当前地点，场景期间按固定参与名单演出。

这里的“集合/传送”不修改任何角色位置、作息、到访、关系或世界变量。实现方式是：

- 场景状态保存发生地点和固定参与名单；
- AI 快照按固定名单注入在场角色；
- UI 从进行中的特殊场景派生临时在场头像。

### 头像点亮规则

- 场景开始后，所有参与妻子和需要演出的丈夫头像在当前场景栏临时点亮；
- 头像点亮仅用于给玩家明确反馈，让玩家看见“人已经到齐”；
- 它只是 UI 表现，不代表角色的日常位置真的改变；
- 不写入角色位置变量，不触发撞见、到访、丈夫作息、地图巡游、冷落计时或其他普通在场结算；
- 场景结束、取消、回档到启动前或状态失效后，临时头像立即熄灭，恢复普通位置推算；
- 刷新页面和同楼重掷时，头像必须能从特殊场景状态重新派生，不能依赖 Vue 临时内存。

## 六、单一紧凑状态

为避免九种场景各自扩散变量，只保留一个通用的进行中状态对象。字段最终以代码实现为准，语义至少包括：

```yaml
系统:
  _特殊场景:
    id: ''             # 空=没有场景进行中
    当前轮: 0          # 已成功落地/正在生成的轮次由实现明确区分
    总轮数: 0
    地点: ''
    参与妻: []
    演出妻: []
    演出夫: []
    启动楼层: -1
```

完成记录继续共用：

```yaml
系统:
  _已完成特殊场景: []
```

不得为九种场景另建九组“进行中、当前轮、角色到场、奖励已发”等布尔变量。

## 七、多轮推进

每种特殊场景后续必须单独配置：

- 总轮数；
- 开场节拍；
- 每轮主题与必须发生的关键动作；
- 本轮允许 AI 自由发挥的范围；
- 每轮需要呈现的角色；
- 场景底线和禁止提前发生的后续内容；
- 最终轮的明确收束条件。

运行纪律：

1. 赠送成功后建立状态并排队第一轮；
2. 每次生成只注入当前轮节拍，不得提前跨轮；
3. AI 正文成功写回后，当前轮才推进；
4. 同楼重掷重放同一轮，不重复推进；
5. 生成失败、取消或输出未落地时不推进；
6. 普通道具事件、手机事件和其他系统事件不得抢占或冲掉场景节拍；
7. 场景期间地点和参与名单保持锁定；
8. 只有最终轮正文成功落地后才完成场景。

九种场景的具体轮数与逐轮玩法尚未拍板，当前不得用统一三轮模板或一次性剧情代替。

特殊场景默认是支线奖励，不向参与角色上报主线线路事件，也不因为“参与过任意特殊场景”改变主线侧写。只有明确写进个人线路配置的场景（例如「肉偿账本」）才能作为对应主线节点。

## 八、完成结算

特殊场景最终轮成功落地后，按顺序执行：

1. 将场景 id 写入 `_已完成特殊场景`；
2. 对本次固定名单中的每位参与妻增加堕落值 `+2`；
3. 仅当该场景明确接入个人主线时，向指定参与妻上报“特殊场景”阶段线路事件；
4. 清空 `_特殊场景` 进行中状态；
5. UI 临时头像熄灭并恢复普通场景推算；
6. 特殊场景票从背包移除。

为保证失败和回档自洽，场景票可在启动时标记为占用，但其最终消耗语义必须与场景状态处于同一本 MVU 楼层快照中；最终轮未成功落地不得永久吞票。

## 九、数值与世界状态铁律

特殊场景不承担九套独立变量结算。

唯一固定角色数值奖励是：

- 每位参与妻：堕落值 `+2`。

除此之外，特殊场景不得直接修改：

- 好感值；
- 婚姻值；
- 身体开发；
- 妻子的穿戴、性癖槽或永久状态；
- 丈夫疑心值、信任值、结局轨道；
- 欠租、现金、胜任度、风闻；
- 微信、朋友圈、录像或照片记录；
- 日常位置、作息和撞见计数；
- 任何场景文案中提到但没有单独系统授权的世界事实。

因此，旧版“肉偿账本购买时立即清零欠租”的专属脚本结算必须移除。剧情可以表现一次特殊的账本主题事件，但特殊场景系统本身不改欠租。

头像临时点亮不属于角色变量奖励，也不得被其他系统当作真实位置变化消费。

## 十、回档、重掷与异常

- 回档到购买前：现金和背包随快照恢复；
- 回档到启动前：场景未进行，头像不亮；
- 回档到场景中：恢复同一地点、参与名单和当前轮；
- 回档到完成前：奖励和完成记录不存在，可继续或重新演；
- 回档仍在完成后：保持已完成，不再上架或购买；
- 同楼重掷：相同参与名单、相同轮次、相同场景票状态；
- 生成失败：不推进、不奖励、不登记完成；
- 数据损坏或配置缺失：安全中止场景并恢复场景票，禁止半结算。

## 十一、交互幕与三种操作

特殊场景只有少数预先指定的节拍会在 AI 正文之间插入“交互幕”，普通节拍仍是正常的 AI 正文与玩家输入，不要求操作小游戏。交互幕只允许三种操作，电脑和手机共用同一套 Pointer Events：

1. **单击/轻触**；
2. **连续点击/连续轻触**；
3. **长按**。

不采用双击、拖动、滑动、右键、悬停、滚轮、多指、压力感应或轨迹绘制作为特殊场景操作。

鼠标左键和手机单指轻触视为同一种输入。禁止出现只有电脑玩家能完成的提示，例如只写“点击鼠标左键”；界面主文案应写“连续点击 / 连续轻触”，电脑端可附带鼠标说明。

### 交互幕视觉

- 每个交互幕至少配置“操作中图”和“通过结果图”两个明确状态；
- 图片可以直接画出震动、残影、速度线、抖动轮廓等效果，让静态画面假装响应玩家操作；
- 前端可在点击或长按过程中叠加轻量 CSS 位移、缩放、亮度或震动反馈，但不要求实时生成新图；
- 图片加载失败时必须显示可操作的占位背景和瓷砖，不能让剧情卡死；
- 交互图片属于场景演出素材，不自动登记为角色变量、身体状态或世界事实。
- 操作成功后不得直接隐藏图片，必须把“操作中图”切换成对应的“通过结果图”，让玩家得到明确的视觉回报；
- 通过结果图在 AI 续回合生成期间继续显示，用来承接操作结果并覆盖等待时间；下一轮正文成功落地后，再由下一节拍决定保留、替换或收起。

### 进入交互幕时的原子切换

上一轮 AI 正文成功落地且下一节拍被配置为交互幕后，前端一次性完成：

1. 保留刚生成的 AI 正文数据，但暂时隐藏其正文显示；
2. 在原正文框架的主展示位显示交互图片；
3. 在图片下方显示一个或多个瓷砖块操作按钮；
4. 隐藏文字输入框和发送按钮；
5. 锁住地图移动、背包、商店、手机和其他会切换场景或触发生成的入口；
6. 只开放当前交互幕规定的单击、连续点击或长按操作。

“隐藏正文”只改变当前主展示位的可见性，不删除聊天楼层，不修改 AI 原文，也不另建一份正文副本。该段正文仍保留在聊天历史或史册中，但交互成功后不会重新回到主展示位。

特殊场景不存在“玩家偏好正文隐藏”的设计。进入交互幕时一律隐藏当前正文；新 AI 正文成功落地后，一律显示新正文。现有眼睛按钮的普通阅读开关不作为场景条件，不继承到交互幕，也不生成任何偏好变量。

这些 UI 变化必须由同一个交互幕状态派生，不能分别依赖多个互相竞争的 Vue 临时布尔值，避免刷新后出现“图片和正文同时显示”或“输入框提前出现”。

### 连续点击

- 玩家对指定瓷砖或图片热区连续点击；
- 脚本按有效时间窗和目标次数累计；
- 每次有效点击提供即时视觉反馈；
- 超时、点错区域或节奏断开可判定本次尝试失败并重置当前尝试进度；
- 点击过程中只在前端临时内存累计，不为每一下点击写 MVU；
- 达成目标后只向场景状态提交一次“本交互已完成”。

长按同理：按下时开始本地计时，松开、失焦、手指滑出有效区域或页面被系统中断时判定是否达标；只有最终成功/失败结果进入场景状态。单击则在一次有效操作后直接提交结果。

### 失败与补偿通过

- 交互失败不扣数值、不消耗场景票、不改变角色态度，也不调用 AI；
- 失败后允许立即重试；
- 连续失败达到配置阈值后，显示一个明确的补偿瓷砖按钮；
- 补偿按钮可直接将当前交互判为通过，确保手机性能、触控延迟、无障碍需求或设备事件丢失不会形成剧情死锁；
- 补偿通过与正常操作成功在剧情和奖励上完全等价，不留下羞辱、降档或“辅助模式”变量；
- 失败阈值及补偿按钮文案由各交互幕配置，默认值待九种玩法讨论时确定。

### 成功后的结果图与生成顺序

交互成功后严格按以下顺序执行：

1. 立即锁定成功结果，禁止重复点击触发第二次；
2. 将操作中的图片切换为通过后的新图片；
3. 隐藏进度反馈和全部瓷砖块，但保留通过结果图；
4. 上一段触发交互的 AI 正文继续保留在历史中，但不恢复到当前主展示位；
5. 将交互成功作为下一节拍的既定事实，只触发一次新的 AI 回合；
6. AI 生成期间继续显示通过结果图和正常生成等待状态，同时保持文字输入框隐藏；
7. 新 AI 正文成功落地后，由新正文直接接管当前主展示位，上一段正文不在此处闪回；
8. 推进特殊场景轮次；
9. 若新正文之后配置了新的交互幕，则按该节拍显示新的操作图和瓷砖；
10. 若之后允许玩家自由输入，则重新显示输入框；
11. 若新 AI 生成失败，保留通过结果图和已通过的交互结果，提供“重试生成”，不得要求玩家重新完成操作。

输入框不能在“AI 开始生成”时立即出现，只能在新回复成功完成且下一节拍允许自由输入时出现，避免玩家在生成中重复提交。

交互幕不是特殊场景每回合的固定组成。每个场景应混合使用三类节拍：

- **纯 AI 节拍**：AI 根据本轮主题继续演出；
- **自由输入节拍**：显示输入框，由玩家正常回应；
- **交互幕节拍**：隐藏当前正文和输入框，显示操作图、瓷砖及通过结果图，并在成功后自动续写。

同一场景连续安排多个交互幕应视为例外，避免玩法变成重复点按。是否插入交互幕必须服务于具体动作和画面变化，而不是为了每轮都让玩家操作。

### 防并发纪律

- 一个交互幕只允许一个完成事务；
- 正常通过、补偿通过和重复点击必须竞争同一把提交锁；
- 成功后最多发起一次 AI 请求；
- AI 请求进行中，所有交互瓷砖和补偿按钮均不可再次触发；
- 刷新、回档和同楼重掷后，界面完全由 MVU 中的场景轮次与交互状态重建；
- 高频点击不得直接逐次写 MVU、逐次调用事件总线或逐次触发 AI。

交互状态作为通用 `_特殊场景` 对象中的一个紧凑子对象保存，不为九种场景分别建立变量。建议语义如下，最终字段以实现为准：

```yaml
交互:
  id: ''
  类型: ''          # 单击 / 连续点击 / 长按
  状态: ''          # 待操作 / 已通过 / 等待AI
  失败次数: 0
  补偿可用: false
```

点击次数、按住毫秒数、指针坐标和动画帧只存在于前端临时内存，不进入 MVU。

## 十二、九种场景待讨论项

以下内容留到下一步逐场景讨论：

- 每场总轮数；
- 可接受的赠送对象；
- 动态参与者的选择规则以及是否允许玩家选择；
- 丈夫在哪些轮次出现；
- 每轮主题、关键镜头和收束；
- 场景是否允许玩家中途主动退出；
- 中途退出是否可续演，以及场景票如何处理；
- 最终轮完成判据；
- 九种场景具体文案与玩法差异。
- 哪些轮次插入交互幕；
- 每个交互幕使用单击、连续点击还是长按；
- 对应图片需求、点击目标、次数/时长、失败阈值与补偿按钮文案。
