## 三、用户反馈与设计目标

玩家截图显示 `_待发送事件` 中积压了：

```text
【翻垃圾的收获】
【心照不宣】
【事件在场妻:101】
【上一动作·送礼回响】
【事件关联妻:101】
```

旧系统把以下状态全塞进同一条字符串：

- 条件已满足但尚未到设计场景；
- 已在正确场景触发、正在生成；
- 生成失败、等待原场景重试；
- 多个系统先后产生的剧情；
- 给 AI 使用的导演指令与角色绑定标签。

旧消费语义近似：

> 下一个成功正文回合，把 `_待发送事件` 的所有内容一起演掉。

因此会发生：

- 离开垃圾房后，在 302 或其他房间演“翻垃圾的收获”；
- 在 101 与夏乔互动时，突然插入 202 搬入；
- 多个剧情族同楼混演；
- UI 把 `事件在场妻:101` 等机器标签显示给玩家。

用户拍板方向：

```text
条件满足
→ 创建带目标场景的剧情票
→ 只有抵达设计场景才激活
→ 激活后持久锁场
→ 成功才消费并解锁
→ 失败／取消／超时仍停留原场景，只重试正文
```

必须区分：

### 1. 等待到场票

- 条件已满足；
- 玩家当前可能在其他场景；
- 不注入当前无关正文；
- 不打断当前 101 等互动；
- 到设计地点后才允许激活；
- 可以阻止时间推进；
- 不应让机器标签承担玩家标题。

### 2. 活动场景事务

- 业务已经在正确地点提交；
- 同一时间最多一张；
- 保存目标场景、标题、导演内容、原行动、触发时段／楼层与请求世代；
- 完成前锁定当前地点及会改变状态的入口；
- API 失败、取消、超时后进入待重试；
- 重试只重新生成正文，不重复扣物品、抽线索、写冷却、发奖励或推进节点。

## 四、不可回退的语义约束

1. **业务前先拿生成租约。**
   若手机、数据库或前台生成槽一开始就忙：动作尚未发生，绝不能扣物品、写冷却、抽线索或创建活动票。

2. **业务已提交后生成失败。**
   业务结果和同一活动票保留，玩家原地点击“重试本段剧情”；不能再次执行业务。

3. **请求世代。**
   每次重试增加 `请求世代`，旧请求迟到不得认领新世代。

4. **取消只取消当前生成尝试。**
   不取消业务、不清票、不解锁场景。

5. **刷新／重载。**
   活动票来自 MVU，刷新后恢复标题、目标地点、待重试入口与锁场。

6. **回档／重掷／swipe。**
   活动票随消息分支快照：
   - 回到触发前：业务和票一起消失；
   - 回到触发后、演出前：恢复待重试；
   - 旧分支迟到结果不得写入新分支；
   - 重掷成功楼后，应恢复同一票并重演正文，不重算业务。

7. **一次最多一张活动票。**
   后续剧情只能等待，不能与当前票同楼混演。

8. **机器协议不进入 UI。**
   `事件在场妻`、`事件关联妻`、`阶段线路演出`、`场景剧情:v1` 等只能供脚本消费。

9. **特殊场景不重复套普通票。**
   录像带、静音会议、荣耀洞已有独立多拍状态机；普通场景事务必须避开它们，防止两套重试门互锁。

10. **等待远处的票不应冻结当前无关互动。**
    例如 202 搬入在楼梯间等待时，玩家可先结束 101 当前互动；只有到达目标地点后才锁场。会新建另一段强制剧情的操作必须逐项审查，不能再次形成混积。

## 五、当前采用的兼容架构

当前代码没有新增一张完全独立的“等待票数组”，而是采用兼容迁移方案：

```text
_待发送事件
  仍保存等待队列与 AI 导演载荷
  每张新票添加结构化机器标记

_场景剧情事务
  只保存当前唯一活动事务的所有权

_已注入事件
  继续负责同楼重掷重放
```

结构化标记形如：

```text
【场景剧情:v1:<编码ID>:<编码目标场景>:<编码玩家标题>】
```

这符合此前讨论中的原则：可以保留 `_待发送事件` 作为旧档兼容和 AI 文本载荷，但它不再单独承担活动所有权。
