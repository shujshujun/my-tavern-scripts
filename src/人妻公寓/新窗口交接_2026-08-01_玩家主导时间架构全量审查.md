## 2. 用户已经拍板的产品规则

以下不是建议，而是当前实现必须遵守的规则：

1. 世界时段不再由 AI 或普通聊天自动更新，只由玩家显式按钮推进。
2. 一天固定六个时段：`早上 → 中午 → 下午 → 傍晚 → 晚上 → 深夜`。
3. 世界时间从 `第1周／星期一／早上` 开始；用星期变量让人物不同星期去不同区域。
4. 妻子基础位置由固定周作息决定，脚本准确计算，不再让 AI 猜，也不按消息楼随机。
5. 旧存档无需兼容旧钟楼时间；没有新时钟时直接从绝对时段 `0` 开始。
6. 玩家可以连续刷时段，不设每日推进次数上限。不要把连续合法推进当作弊修掉。
7. 当前按钮地点规则：
   - 管理员室：`推进一时段`＋`睡到次日早晨`。
   - 302：只有`睡到次日早晨`。
   - 其他房间、楼道和公共区域：当前没有时间按钮；后端也拒绝伪造请求。
8. 从 302 睡觉后仍在 302 醒来；从管理员室睡觉或推进后仍在管理员室。
9. 用户后来问过“其他地方不能推进时间吗”，当时只向用户说明了当前行为，并提出过“全地点可等待”的可能方案；用户没有拍板修改。新窗口不得自行把推进按钮全局化。
10. “普通聊天”当前指现场主输入框的一次玩家输入＋AI 回复。它增加正文消息楼，但不改变世界时段。
11. 微信不受未来精力值限制。未来精力只限制现场主输入框/面对面 AI 对话；微信私聊、朋友圈、手机事件、系统按钮和重掷不消耗精力，精力耗尽也不能锁手机。
12. 精力与体力尚未实现，本轮只能审查时间地基是否为下一阶段留出了可靠入口。
13. 管理员室属于合法公共区域；新住户去管理员室报到符合用户要求。
14. 时间按钮沿用现有代码原生 SVG 图标和 CSS 皮肤，不需要 AI 生成按钮图片。

风闻、胜任度仍暂停。不要因为旧交接标题包含它们便恢复讨论或修改数值。

## 3. 当前时间架构的唯一真值

### 3.1 世界时间轴

唯一持久字段：

```text
系统._绝对时段
```

语义：

- `0`：第1天、第1周、星期一、早上。
- 每 `+1`：进入下一个时段。
- 每 `6` 个时段：下一天。
- 每 `42` 个时段：下一周，同一星期作息循环复现。

核心文件：

- `src/人妻公寓/周作息.ts`
- `src/人妻公寓/脚本/游戏逻辑/楼层时钟.ts`
- `src/人妻公寓/schema.ts`
- `src/人妻公寓/世界书/变量/initvar.yaml`
- `src/人妻公寓/世界书/变量/变量更新规则.yaml`

核心读取口：

- `取绝对时段`
- `读取世界时间`
- `当前时段`
- `当前天数`
- `当前周数`
- `当前星期`

唯一底层推进原语：

- `推进时段`
- `推进到次日早晨`

业务代码不得直接调用推进原语绕过中央结算。当前预期只有 `时间推进系统.ts` 调用它们；另有 schema 迁移归一和新游戏置 `0`，这些不是业务推进。

### 3.2 正文消息楼轴

消息楼仍然存在，但只负责：

- 正文历史与上下文。
- 回档、重掷、同楼 swipe/分支。
- 事件注入与同楼重放。
- 数据库时间线栅栏。
- 场景进入、粘滞、离场和连续对话。
- 特殊场景拍次与父亲通话收尾定位。
- 微信消息、朋友圈和图片轮换的历史锚。
- 冷落余波的“需要几条有效当面安抚正文”。
- 深夜夜访等明确写成“每个现场正文楼一次”的代价。
- 雌竞争近期互动等剧情回合距离。

普通正文增加消息楼，但必须保持 `_绝对时段` 不变。

不要看见“楼层/钟楼”就机械替换。下列旧名字在新局中实际存绝对时段或其派生值：

### 3.4 第三类：真实墙钟毫秒

项目仍合法使用`Date.now()`、`setTimeout`和`setInterval`处理：脚本心跳、请求超时、数据库稳定采样、长按识别、生成等待计时、唯一消息ID和手机外壳的现实钟表显示。这些不是游戏世界时间。

审查时必须确认真实毫秒没有参与人物作息、经济期、冷落、冷却或剧情等待；同时也不要把纯超时/心跳代码误迁到`_绝对时段`。

## 4. 玩家时间按钮与中央事务

### 4.1 界面接线

文件：`src/人妻公寓/界面/客户端/App.vue`

当前行为：

- 管理员室当前在场时显示时钟按钮和月亮按钮。
- 302 当前在场时只显示月亮按钮。
- 点击后载荷携带 UI 看到的 `预期绝对时段`。
- `发送中` 立即置真，地图、现场输入、回档/重掷等共享界面锁，直到脚本发出结束信号。
- 成功由 `人妻公寓:回合完成` 刷新；失败由 `人妻公寓:时间推进结束` 解锁。
- 连续完成后再次点击是用户允许的刷时段；同一事务尚未结束时的重复点击必须被挡住。

### 4.2 脚本入口

文件：`src/人妻公寓/脚本/游戏逻辑/index.ts`

入口事件：

- `人妻公寓:推进时段`
- `人妻公寓:睡到次日早晨`

必须先于任何场景清理检查：

- `_时间推进中` 互斥。
- 当前房间与请求方式的组合。
- 序章是否完成、是否坏结局。
- AI/正文/写入/隔离事件是否进行中。
- 特殊场景、荣耀洞、父亲通话、调查待选。
- 是否有未演出的非时间强事件。
- `预期绝对时段` 是否仍等于存档真值。

后端不信任载荷里的“方式”，两个 listener 各自强制映射固定方式。

地点规则必须由后端执行：

```text
推进一时段：仅管理员室
睡到次日早晨：管理员室或302
```

时间动作成功前会清理连续场景相关 chat 变量；若事务或 stat 写入失败，要逐项恢复原 chat 值。302 睡眠的 `_场景.房间id` 必须保持 `302`，不能醒来被传送到管理员室。

### 4.3 中央原子事务

文件：`src/人妻公寓/脚本/游戏逻辑/时间推进系统.ts`

入口：

```text
执行时间推进事务(data, { 方式, 预期绝对时段, 当前消息楼 })
```

当前事务先深拷贝候选数据；校验失败或中途抛错时，传入原对象必须深度零变化。成功顺序是：

1. 推进绝对时段。
2. `惰性结算全楼`。
3. 刷新所有丈夫状态栏。
4. `经济结算`，跨多个账期时逐期循环。
5. `结算全楼冷落`。
6. `上报时段推进`，这是阶段线路唯一合法“时段经过”入口。
7. 若抵达早上，处理母亲首夜早饭桌事件。
8. 没有更强事件时执行入住检测。
9. 仍无强事件时写一条可覆盖的普通`【时间流逝】`事件。
10. 最后才用候选替换原对象并持久化。

事件优先级必须复核为：

```text
坏结局/已有未演强事件（推进前阻断）
> 推进过程中产生的强事件
> 母亲次日早饭桌
> 新住户首次登场预约
> 普通时间流逝文案
```

已有单一普通时间流逝文案允许被下一次刷时段覆盖；其他强事件绝不能被标签伪装后吞掉。

`旧钟楼跨度转时段`只允许换算源码里的旧平衡常量，不得用于迁移旧存档时间戳。

## 7. 新窗口必须优先排查的高风险点

### 7.1 “至”字段的端点是否多算一档

当前`丈夫在楼`使用：

```text
夫._外出至 >= 当前绝对时段
```

道具则把截止写为：

```text
当前绝对时段 + 配置持续时段
```

`_疑心冻结至`也使用类似包含端点。必须用表格逐时段验证：从时段 `T` 使用“持续3时段”道具，究竟应该覆盖 `T,T+1,T+2`，还是还包含`T+3`。不要仅凭旧行为下结论；对照文案和配置语义后，若确认 off-by-one，补失败测试再修。

### 7.2 普通回合仍有幂等结算回调

`回合引擎.ts`与原生 MVU 路径的`index.ts`仍会调用`经济结算`、`结算全楼冷落`等函数。它们现在读取不变的绝对时段，理论上靠水位幂等，不会让普通聊天推进或重复扣账。

必须验证：

- 同一时段连续聊20轮，现金、房租期、婚姻被动账、冷落日、丈夫外出窗口不重复结算。
- 普通回合不会生成新的时间线路节点。
- 这些回调作为加载/旧数据校准后备是否仍有必要；不要未经测试直接删除。

### 7.3 睡眠跨多期不是只看终点

从早上睡到下一早上会跨6时段；从深夜只跨1时段。每个起点都要测试：

- 经过时段数。
- 跨天/跨周标记。
- 多经济期逐期结算。
- 被动结算乘以完整差值。
- 冷落按跨过的完整天累计。
- 手机旧异步任务失效。
- 最终事件优先级。

### 7.4 302睡眠与入住登场的场景关系

从302睡眠成功后，chat场景保持302。入住检测仍应服从首次登场公共场景门，因此不能把新住户报到强行塞进302；条件必须保留，玩家回到管理员室等合法公共场景后可补发。管理员室睡眠则可以在场景空闲时触发报到。

这条目前主要靠静态接线和既有入住门测试间接覆盖，需要新增运行级组合测试。

### 7.5 时间按钮不创建正文楼的持久化语义

时间事务直接写 stat 并发`回合完成`，不创建一条新的普通 AI 正文。必须人工或集成验证：

- 点击后立即刷新页面，世界时间仍保存。
- 连刷后再聊天，下一正文快照继承最新时间。
- 清空的`_上次回合`使重掷不会重放推进前剧情。
- 回档到更早真实正文楼时，世界时间、手机节拍、场景和数据库各自恢复到一致状态。
- stat写入失败时，绝对时段和被清掉的chat场景都完整回滚。

### 7.6 顺序刷允许，并发刷必须拒绝

产品允许“事务完成后继续点”。应测试：

- 同一旧水位的两个同时请求，只成功一个。
- UI锁还未解除时重复点击无效。
- 旧iframe或伪造的陈旧`预期绝对时段`失败且数据零变化。
- 第一笔完成并刷新水位后，下一笔新请求可以正常成功。

不要增加每日次数限制或人工冷却。

### 7.7 同一时段随机与刷新点

金币、垃圾、偷窃、打断、撞见、荣耀洞、手机内容等使用确定性种子。应确保：

- 同一绝对时段重掷或刷正文不会换结果。
- 到配置规定的新时段/新周期才换结果。
- 仅用于历史展示的随机（例如按微信消息楼稳定点赞数）可以继续使用消息楼，不应误报。

### 7.8 交接前独立只读复核发现的待确认风险

下面几项不是已经修复的结论。新窗口应把它们放在审查最前面，先写复现或最小测试，再决定严重度与修法：

1. **事务中途产生坏结局后仍继续结算**：`时间推进系统.ts`当前在`经济结算`之后无条件继续`结算全楼冷落`和`上报时段推进`。若跨期经济结算在这一笔内刚设置`_坏结局`，同笔仍可能继续降低人物数值、推进关系线路或发放线路物品。现有测试只覆盖“进入事务前已经坏结局”，没有覆盖“经济结算中产生坏结局”。需要明确 Game Over 的事务截断语义。
2. **管理员室睡眠与母亲早饭桌的空间一致性**：从管理员室睡眠后场景仍是管理员室，但母亲早饭桌事件写的是302厨房，并通过事件角色标记强制母亲在场。要验证实际快照是否会把“302厨房早饭”演到管理员室。302睡眠保持302本身是正确的；管理员室睡眠遇到该事件时应如何落点，需要以用户意图和场景系统一致性决定。
3. **切换聊天竞态**：时间入口有时段乐观锁，却没有像手机异步任务那样保存`当前聊天ID`并在每个异步边界复核。若玩家通过酒馆外层在`updateVariablesWith`、stat写入或回滚期间切聊天，时间数据、`message_id:-1`写入和chat变量恢复可能落到另一聊天。要做真实或mock的切聊竞态测试。
4. **跨存储原子性只做了静态检查**：MVU候选数据失败可零变化，chat场景清理失败有catch恢复，但尚无运行级测试模拟“chat清理成功→事务成功→stat写入失败”以及恢复本身失败。必须验证不会留下“时间没走、人物却散了”或反向覆盖新聊天。
5. **textarea仍可编辑**：时间事务中提交、Enter、地图、房卡动作、重掷和回档都有门，但主textarea本体没有`disabled/readonly`，玩家仍可输入，只是不能提交。若产品要求“输入锁”包含不可编辑，应新增只读/禁用状态但保留用户已输入文本；如果允许预先打字，则应把现状写成明确交互规则。
6. **锁测试覆盖不足**：现有按钮测试主要断言置锁与失败解锁，没有完整锁定地图按钮、房卡动作、发送函数、重掷函数以及后端玩家行动/回档/原生生成的全部互斥点，也没有真实浏览器E2E。
7. **唯一写入口测试标题强于断言**：已有测试声称中央事务是唯一业务入口，但没有对全源码所有`_绝对时段`赋值与推进原语调用做完整断言。应强化成真实文件扫描。
8. **低危注释陈旧**：`index.ts`仍有“只能从管理员室的两个显式按钮推进”的旧说明，现已有302睡眠特例。审查代码时不要被该注释误导，确认行为后顺手改准。
9. **快速连刷可能漏掉最终手机节拍**：`手机节拍`与`冷落预警节拍`各自采用“已有任务就直接返回”的互斥。旧任务会在绝对时段变化后因租约失效，但新时段触发的节拍可能恰好因旧任务仍在运行而跳过，且旧任务退出后没有自动补跑。普通朋友圈漏一拍也许可接受，冷落预警属于玩法硬提示，必须用延迟AI＋连续推进复现。
10. **重复入口最外层早退不发结束信号**：`_时间推进中`为真时，第二个入口只发提示后直接返回，不发`时间推进结束(false)`。单iframe因`发送中`通常不会走到这里，但多iframe、切聊天后的新界面或手工事件可能让第二个界面一直锁住。需要决定结束信号应按请求/界面关联，避免简单广播又错误解锁第一笔。
11. **可覆盖时间事件识别可能过宽**：当前只检查文本以`【时间流逝】`开头、标签只出现一次且不含`|`。异常旧数据若把另一强事件直接拼在后面而没有竖线，可能仍被下一次推进覆盖。应构造畸形旧事件验证失败关闭策略。
12. **跨多时段睡眠只广播一次线路事件**：一次睡眠不管跨1还是6时段，都只调用一次`上报时段推进`，所以最多完成当前一个线路节点。这符合“一次玩家动作一次线路事件”的现实现，但应写测试锁成明确规则，防止后人误按跨过时段数循环推进四个节点。

### 7.9 消费者全量扫描发现的确认缺口

以下问题已经从当前源码确认到完整调用路径，但新窗口仍应先补失败回归，不能直接凭交接盲改：

1. **阶段线路没有真正执行下午/傍晚/夜晚条件**：`阶段线路系统.ts`的`事件匹配文本`只拼`标识＋地点＋服饰`，完全没有拼入`事件.时段`。大量节点文案与关键词包含“下午、傍晚、夜、晚”，但这些词当前不是时间硬门。`App.vue`虽然传当前时段，早上仍可能展示并完成“今晚/傍晚/深夜”节点。更重要的是，现有正则通常把地点与时段写在同一个`/地点|夜|晚/`中，即使简单把时段拼进去也只是OR，不能表达“地点正确且时间正确”。需要把地点条件和时段条件结构化拆开。
2. **阶段地点监听信任前端地点/时段**：`index.ts`的`人妻公寓:线路到达地点`直接采用载荷中的`地点、门牌、时段`，没有从`读场景()`与`_绝对时段`重新派生复核。旧界面、第三方主题或手工事件可伪造线路条件。修复时必须同时处理UI展示与后端权威门。
3. **102“门缝那一眼”可在任意时段触发**：`结算系统.ts:绿帽线检测`的注释和强制事件都写“某个傍晚/这个傍晚”，但代码只拿绝对时段做随机种子，没有`当前时段(...) === '傍晚'`校验，会与HUD时间和固定作息冲突。
4. **手动楼务群/姐妹群迟到回复可跨时段写回**：自动手机节拍、冷落预警、邀约和普通单聊已有聊天ID＋消息锚＋绝对时段租约；玩家手动发楼务群/姐妹群时，两个分支直接等待AI后写库，没有租约。生成期间推进时间、切聊、swipe或回档后，旧回复仍可能携带旧`时`写入新状态。
5. **商店“次日达”只有文案，没有时间机制**：App与注释明确写“次日达·送到管理员室”，`商店系统.ts:购买`却立即扣款、立即入包，Schema没有配送队列或到货绝对时段。若“次日达”只是装饰，应改准文案；若它是玩法承诺，则需设计跨日到货、地点提示、回档和强事件优先级。不要擅自选择方案，先向用户说明差异。

### 7.10 额外高风险维护边界

1. **对饮只靠UI检查丈夫是否在家**：`侦探系统.ts:对饮`业务函数自身不复核`丈夫在楼(...) === '在家'`，伪造/旧界面事件可在丈夫外出时消耗酒并完成酒局。每日工具由头的同日次数也主要由App控制，需要审查后端和原生输入能否绕过。
2. **微信节拍对象混存不同单位**：`_微信.节拍`多数键存绝对时段，但`圈图:*`存图片编号。`回合引擎.ts:裁手机时间线`回档时把所有节拍值统一`min(value, 目标钟)`，可能把图片游标当世界时钟裁坏。应拆类型/命名空间或只裁真正的时间键，并补回档测试。
3. **旧手机记录缺`时`会随当前时段漂移**：渲染旧记录时若用当前绝对时段兜底，玩家推进后历史消息的显示时间可能改变。需要稳定迁移、固定未知标识或明确接受，不应每次读取当前钟。
4. **深夜叙事可能绕过世界时钟**：`制服夜巡`、`露出癖`开幕等配置固定写深夜，但启动入口未必校验当前时段；钓鱼“周末”等也可能只是即时剧情皮。先区分哪些是硬时间条件、哪些允许独立演出时间泡。硬条件要后端校验；时间泡不得偷偷改`_绝对时段`，提示词应避免与HUD互相否定。
5. **叙事楼注释陈旧**：例如`snapshotSystem.ts`仍可能把“离场六个消息楼”解释成“两个时段”。运行语义仍是叙事消息楼时，只修注释/命名，不要为了对齐文字误迁到世界时钟。

## 13. 新窗口交付标准

新窗口完成审查时，至少向用户提供：

1. 一张完整时间消费者表，明确每项使用绝对时段还是消息楼。
2. 按严重度列出的真实问题；没有复现证据的只写“待确认风险”，不要直接定性。
3. 每个修复的根因、触发路径和新增回归。
4. 六时段、跨日、跨周、跨多经济期、顺序刷、并发刷、302睡眠的实际结果。
5. 普通聊天和微信均不推进时间的证据。
6. 191项现有回归以及新增测试、构建、目标目录类型检查结果。
7. 明确说明是否仍存在无法在当前环境完成的真实浏览器端验证。

只有完成上述矩阵后，才可以向用户说“所有需要时间的功能已经仔细审查”。
