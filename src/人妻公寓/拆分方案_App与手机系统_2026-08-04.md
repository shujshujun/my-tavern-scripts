# App.vue 与 手机系统.ts 拆分方案（2026-08-04）

> 目标：把两个巨石文件拆成小模块，使任何单次修复只需读取 1~2 个小文件。
> 原则：每个阶段独立可验证（`pnpm build` 通过 + 手动冒烟），拆完一阶段提交一次，任何阶段可中止且不留半成品。
> 本方案基于 2026-08-04 的结构测绘（行号以当日文件为准，后续执行时用 Grep 重新定位，不要盲信行号）。

---

## 一、App.vue（14116 行 = template 2310 + script 4438 + style 7366）

关键事实：

- **CSS 占 52%**（6751–14116），拆分主要工作量在样式搬移，不在逻辑。
- 纯根组件，无 props/emits，全仓只有 `index.ts` 引用它 → 拆分无外部 API 兼容负担。
- 同目录已有正确范式：`store.ts`、`场景状态同步.ts`、`录像带交互状态.ts`、`cgLoadState.ts`、`viewport.ts` 都是被 App.vue 单向引用的纯模块。
- 已知隐患（拆分时顺手修）：script 内**两个素材基址常量版本不一致**（约 2398 行 `@rq0.70` vs 约 4395 行 `@rq0.55`），应合并为一处。

### 目标结构

```
界面/客户端/
  App.vue                 # 只剩：布局骨架 + 事件总线接线(onMounted) + 全局状态提供
  components/             # UI 区块子组件（每个自带 <style scoped>）
    Icon.vue
    设置弹窗.vue 首次准备.vue 序章标题屏.vue
    CG图库.vue 读信.vue 监控.vue 商店.vue 背包.vue 档案卡.vue 地图.vue
    静音会议/*.vue 录像带/*.vue
    正文舞台.vue（最后拆）
  composables/            # 跨组件共享状态与动作
    useUIPrefs.ts         # 主题/字号/省流/减动效/全屏（操作 documentElement 的都在这）
    useScene.ts           # 当前房间/幕房间/在幕中/粘滞在场/时段
    useTurn.ts            # 发送中/流式段/运行阶段/重掷/撤回（全局生成闸门）
    useActions.ts         # 跨区块动作：买/送出/装载/点房/进入/晋阶…
    useAssets.ts          # 素材基址(统一版本)/头像图/立绘/图挂了回退字典
  icons.ts types.ts assets.ts
```

### 关键决策

1. **状态共享走 pinia + composable，不走 props 透传**。`data`（根 computed）各子组件自行 `useDataStore()`；`发送中`（template 出现 58 次）、`静音会议正式中`（跨 6 区块）、`时段` 等高耦合状态放 composable 单例。
2. **onMounted 里 288 行事件接线（12 个 `eventOn('人妻公寓 …')`）整体留在 App.vue** 作为事件总线层，回调改为调用各 composable 暴露的 handler。不要按区块打散订阅。
3. **CSS 按区块跟随组件走** `<style scoped>`；`global.css` 的 `:root` token、`html.rq-dark`、`html.rqgy-full` 不动。注意：
   - 111 处 `:deep()/:global()`，夜间覆盖集中段（约 12560–12677）按目标组件重新归位；
   - 同一移动端断点（540px/720px）在 6 处重复出现，移动端紧凑档（约 12815–13273）横跨多个区块，需逐条拆到对应组件；
   - script 生成的内联 CSS 变量（`--scene-img`、`--垫板浓度`、`--kv-img` 等）拆分后必须仍在消费元素的祖先链上。
4. **模板内直接调用的 ~60 个纯展示函数**随其服务的区块搬进同一 composable/组件；~30 个跨区块动作函数统一进 `useActions.ts`。

### 分阶段执行顺序（风险从低到高，每阶段一次提交）

| 阶段 | 内容 | 规模 |
|---|---|---|
| A1 | `Ic` 内联组件 + 图标库 → `Icon.vue` + `icons.ts`；素材常量合并 → `assets.ts`（修版本不一致）；类型集中 → `types.ts` | 小 |
| A2 | 独立小弹窗：CG图库/CG预览、读信、监控、事件提示词、toast/拾获卡 | 小 |
| A3 | 设置弹窗 + 首次游玩准备（只依赖 localStorage 偏好）+ `useUIPrefs.ts` | 中 |
| A4 | 序章标题屏 | 小 |
| A5 | 商店、背包、档案卡（档案卡状态最局域：`选中档案` 63 次引用几乎全在自身区块内） | 中 |
| A6 | 地图（含房卡/房间动作，注意 `房间动作()` 是 224 行巨型函数，可同步二次拆解） | 大 |
| A7 | 静音会议全套（筹备/互动面板/散会，620 行 script 域）+ 录像带 | 大 |
| A8 | 正文舞台/卷轴/输入/回合 UI —— 与 `发送中`、事件总线三重绑定，**最后拆或保留在 App.vue** | 大 |

每阶段验证：`pnpm build` 无错 → 酒馆内冒烟对应功能 → 对照 git diff 确认只动了目标区块。

## 二、手机系统.ts（5190 行，导出 28 个符号，外部实际只用 15 个）

关键事实：

- 4 个消费方：`游戏逻辑/index.ts`（12 符号）、`回合引擎.ts`（6）、`App.vue`（2+类型）、`特殊场景系统.ts`（1）。13 个导出无人使用（可降内部或删除）。
- 周边 16 个手机*/微信*/私聊* 模块全部是**叶子**（零反向 import），当前全图无环。
- 最大风险：`渲染()` 与 `刷新红点()` 被所有业务层回调 → 直切 UI/引擎必成环；32 处模块级可变状态需逐一定归属。

### 目标结构（`脚本/游戏逻辑/手机/` 子目录，原文件变门面）

```
手机系统.ts               # 门面：仅 re-export 15 个外部符号，消费方 import 不变
手机/
  运行时上下文.ts          # 当前聊天ID/当前手机数据/当前手机绝对时段/末楼（最底层，被全体引用）
  数据层.ts               # T3：微信库类型/读库/写库增量/已读水位/分支隔离/余波身份
  UI刷新.ts               # 注册表：请求重绘()/请求刷新红点()；实现由挂载层注入 ← 破环关键
  生成引擎.ts             # T8 净化/验收 + T9 小生成/API 路由/预设（业务层唯一 AI 出口）
  配置.ts                 # T5 localStorage 配置 + T6 人设素材缓存
  摘要系统.ts             # T10 SQLite 探测 + T12 摘要快照/胶囊/刷新排队 + T11 身份宿主
  内容素材表.ts            # T15a 朋友圈/私聊素材纯数据（~280 行零 I/O，最安全）
  节拍引擎.ts             # T15b 手机节拍（371 行按 6 个内容入口拆子函数）+ 合并现有 手机节拍水位.ts
  冷落预警.ts             # T16
  通知桥.ts               # T14 管理任务/风闻通知 + T13 好友表
  静音会议旁路.ts          # T4 + T7 会场私聊摘要/正文记忆
  壳/
    资源与皮肤.ts          # T17：素材基址/手机CSS(190 行模板串)/图标/头像块
    会话瞬态.ts            # T18：输入租约/草稿/待回复上下文/批次瞬态（可变状态最密集处）
    挂载.ts               # T19：注入/拖拽/缩放/悬浮钮；在此向 UI刷新.ts 注入实现
    渲染/                 # T21 渲染() 882 行按页面分派拆：chats/chat/moments/call/talk/settings
    红点与开合.ts          # T20
  交互/
    邀约与发消息.ts        # T22：邀约队列/群接话/发消息/批次执行
    父亲通话.ts            # T23：自成闭环，边界最干净
```

### 关键决策

1. **先立 `UI刷新.ts` 注册表破环**：业务层（节拍/冷落/通知/发消息/父亲通话）只 import `请求重绘()/请求刷新红点()`；`挂载.ts` 启动时注入真实实现（复用现有 4647/4648 的回调传参模式）。数据层 241/452 行两处直调 `刷新红点` 一并改走注册表。
2. **`库.节拍` 水位键约定**（`圈:${门牌}`/`私:${门牌}`/`群`/`姐妹群`/荣耀键）提炼为常量构造函数放数据层，`回合引擎` 用的 `手机节拍水位.ts` 同步改用，杜绝键漂移。
3. **32 处可变状态逐一定唯一归属**（测绘报告 6.A 表），迁移时只搬定义不复制；`会话待回复上下文` 是 UI 与生成层唯一握手对象，归 `会话瞬态.ts` 并给显式读写函数。
4. **门面文件长期保留**，外部 4 个消费方 import 路径零改动；无人使用的 13 个导出在拆分时降为内部。

### 分阶段执行顺序

| 阶段 | 内容 | 规模 |
|---|---|---|
| P1 | 建 `手机/` 目录 + 门面化（先原样整体移动，`手机系统.ts` 变纯 re-export，验证构建） | 小 |
| P2 | 抽 `运行时上下文.ts`、`内容素材表.ts`、`配置.ts`（无环、低耦合） | 小 |

| P5 | 抽 `父亲通话.ts`（最干净闭环）、`静音会议旁路.ts`、`通知桥.ts`、`冷落预警.ts` | 中 |
| P6 | 抽 `节拍引擎.ts`（含 371 行主循环按 6 入口拆解 + 合并手机节拍水位.ts） | 大 |

## 三、总体安排

- **建议先做手机系统（P1–P8），后做 App.vue（A1–A8）**：手机系统是纯 TS、无 CSS 负担、有清晰的消费方契约，风险更低，可先积累拆分节奏；App.vue 的 CSS 搬移量大，放后面。
- 两条线互不依赖，也可以穿插做。每个阶段控制在一个对话窗口内完成（先 Grep 定位 → 局部读 → 移动 → 构建验证 → 提交）。
- 全程不改任何运行逻辑，只做代码搬移与 import 重排；发现的既有 bug（如素材基址版本不一致）单独小提交修复并在提交信息中注明。
