## 一、审查结论

当前四幕主链可以按“初谈→三人摊牌→一次封存并真实独住→取物/冷静/管理员室交接”走通；一次钥匙封存、丈夫统一作息、可选共同夜晚、201条件式留宿、重复点击和当前新档均有自动化证据。

但本轮独立复审确认 **3项高危运行冲突、3项中危旧档/时间问题、1项低危展示接线债，以及1项发布阻断**。因此当前不能判为可直接发布：坏结局和荣耀洞仍可穿透本线，三人幕演员范围未封闭；旧33阶段迁移也有事实丢失/孤儿亲密状态。

独立《离婚》仍只是后续占位，不属于四幕承接已经完成的法律结果；本报告未把它误判为四幕BUG，但发布说明必须准确表述范围。

## 五、逐项问题登记

### XU-001 坏结局后仍可上架并启动《分居》

- **分类：** NEW-FEATURE-BUG／硬生命周期冲突
- **严重度：** P1 高
- **设计初衷：** 坏结局是全局终局，任何新路线不能再写入开始状态。
- **正常运行：** 上架、购买和后端执行均应重新检查 `_坏结局`。
- **对游戏的作用：** 阻止终局后世界继续产生新的婚姻路线事实。
- **BUG为什么出现：** 许曼君上架函数和硬互斥函数都未消费 `_坏结局`；商店没有可替代业务函数门。
- **影响对象与兼容性：** 终局存档仍能领取并把阶段写成“待初谈”；会污染终局快照、商店与后续作息语义。
- **复现：** 在满足L5/交易快感/肉偿账本的201档设置 `_坏结局`，调用上架和购买；REPRO-XU-01稳定通过（即问题稳定复现）。
- **当前证据：** `许曼君分居系统.ts` L148 `function 硬互斥错误(data: SchemaType, 当前地点: string | null = null): string {`；L464 `export function 许曼君分居已上架(data: SchemaType): boolean {`；`audit_repros.tap`。
- **建议修复边界：** 在权威上架、购买和地点动作共同入口统一消费坏结局；不要只隐藏UI。

### XU-002 荣耀洞活动中仍可启动分居动作

- **分类：** CROSS-FEATURE-CONFLICT／强场景单例遗漏
- **严重度：** P1 高
- **设计初衷：** 荣耀洞和普通特殊场景都应占用不可并发的强现场。
- **正常运行：** 业务门应同时检查 `_特殊场景.id` 与 `_荣耀洞拍 >= 0`。
- **对游戏的作用：** 防止两个强剧情共享输入、演员、CG与回合账。
- **BUG为什么出现：** 分居硬门只检查普通特殊场景ID；共享时间系统和《不再留门》都显式识别荣耀洞独立字段。
- **影响对象与兼容性：** 荣耀洞活动时201首幕仍可开放，可能并发生成、写入场景票并污染演员/CG。
- **复现：** 启动分居到待初谈，找到201安全时段后设置 `_荣耀洞拍=0`；REPRO-XU-02仍列出首幕。
- **当前证据：** `许曼君分居系统.ts` L148 `function 硬互斥错误(data: SchemaType, 当前地点: string | null = null): string {`；`时间推进系统.ts` L127 `if (data.系统._特殊场景.id || data.系统._荣耀洞拍 >= 0 || 读取活动场景剧情(data)) return true;`；`audit_repros.tap`。
- **建议修复边界：** 将强现场占用抽到共享权威门，避免每条路线各自漏字段。

### XU-003 远处普通等待票只封死201留宿

- **分类：** CROSS-FEATURE-CONFLICT／时间地点规则漂移
- **严重度：** P2 中
- **设计初衷：** 普通远处等待票应继续排队，只阻塞目标地点；连续锁场/活动事务才全局阻塞。
- **正常运行：** 201睡眠应复用共享时间事务的地点感知判定，再叠加201关系许可。
- **对游戏的作用：** 让公寓其他剧情等待时仍可在合法地点休息，不制造201特例。
- **BUG为什么出现：** 201许可函数直接用 `_待发送事件` 非空作为全局失败；共享时间预检会解析票目标地点。
- **影响对象与兼容性：** 同一存档在管理员室能睡，在201却因101远处票被拒绝，玩家会误以为201许可失效。
- **复现：** 已解锁201留宿，排入目标101的非连续普通等待票；201许可返回失败，而管理员室时间预检成功。
- **当前证据：** `许曼君分居系统.ts` L1051 `if (data.系统._待发送事件) return 失败('还有尚未演出的强制剧情。');`；`时间推进系统.ts` L126 `function 场景剧情阻塞当前时间动作(data: SchemaType, 当前地点: string): boolean {`；REPRO-XU-03。
- **建议修复边界：** 睡眠关系许可与全局时间阻塞分层；201只消费共享地点感知结果。

### XU-004 旧33阶段迁移丢失许曼君已拒绝修复

- **分类：** OLD-SAVE-MIGRATION-BUG
- **严重度：** P2 中
- **设计初衷：** 本地试玩旧档已成立的人物决定迁移后不得重演或反转。
- **正常运行：** 迁移应把旧 `许曼君已拒绝修复` 映射到新 `许曼君已拒绝恢复共同生活`，再决定检查点。
- **对游戏的作用：** 保持人物连续性并避免再次让玩家逼她作同一决定。
- **BUG为什么出现：** 迁移函数读取了 `旧妻拒绝`，但最终赋值只看“双方已同意”，在待第二次封存等阶段写回false。
- **影响对象与兼容性：** 旧档会回到等待私下决定并重演她已经作出的拒绝；不影响新档。
- **复现：** 旧阶段“待第二次封存”＋已取物/修复已提出/旧拒绝=true，经Schema.parse后新拒绝字段为false。
- **当前证据：** `schema.ts` L456 `const 旧妻拒绝 = 旧路线布尔(路线.许曼君已拒绝修复);`；L535 `许曼君已拒绝恢复共同生活: 双方已同意 ? true : false,`；REPRO-XU-04。
- **建议修复边界：** 只在迁移层保留既成正交事实，不改变新四幕主流程。

### XU-005 旧亲密进行中可迁成无真实账本的永久进行中

- **分类：** OLD-SAVE-RECOVERY-BUG
- **严重度：** P2 中
- **设计初衷：** 进行中旧档必须续接真实场次，无法证明时应安全降级为可重试。
- **正常运行：** 绑定标识应与 `_性爱场景` 当前场次、参与者和地点一致；不一致则回到待接受。
- **对游戏的作用：** 防止首次共同夜晚和201长期留宿永久卡死。
- **BUG为什么出现：** 迁移按旧阶段/字段直接保留“进行中”和旧场次标识，没有在迁移后验证真实性爱账。
- **影响对象与兼容性：** 主分居仍能继续，但共同夜晚没有接受动作、不能完成也不能解锁201留宿。
- **复现：** 旧阶段“亲密进行中”、旧绑定存在、当前性爱场景空闲；迁移后仍为进行中且无重试动作。
- **当前证据：** `schema.ts` L490 `const 共同夜晚状态 = 共同夜晚已完成`；`许曼君分居系统.ts` L499 `当前路线.共同夜晚状态 === '待接受' &&`；REPRO-XU-05。
- **建议修复边界：** 迁移后做一次绑定一致性归一化；只降级可疑旧档，不伪造完成。

### XU-006 三人幕缺少演员闭包

- **分类：** CROSS-FEATURE-CONFLICT／AI可写范围污染
- **严重度：** P1 高
- **设计初衷：** 分居三人幕只能有许曼君、赵国强与玩家；其他妻子不得因粘滞/赴约进入可写状态。
- **正常运行：** 像《不再留门》一样，在生成和提交前校验精确演员集合。
- **对游戏的作用：** 保护人物关系、雌竞、亲密候选和AI变量范围。
- **BUG为什么出现：** 事件标记会强制201夫妻，但共享焦点检测会把自然/粘滞妻子合并；分居没有专用演员错误函数。
- **影响对象与兼容性：** 第三名妻子可进入快照与可写范围，分居拍仍提交；共同夜晚还可能污染多人亲密候选。
- **复现：** 把101妻粘滞到201，再启动分居三人幕；焦点含101和201，提交仍成功。
- **当前证据：** `许曼君分居系统.ts` L172 `function 事件角色标记(参数: { 在场妻?: 门牌[]; 在场夫?: 门牌[]; 关联妻?: 门牌[]; 关联夫?: 门牌[] }): string {`；`snapshotSystem.ts` L389 `妻在场: _.uniq([...事件妻, ...结果.妻在场]),`；REPRO-XU-06。
- **建议修复边界：** 增加路线级精确演员闭包，并在两条正文通道提交前复核；不要只改提示词。
