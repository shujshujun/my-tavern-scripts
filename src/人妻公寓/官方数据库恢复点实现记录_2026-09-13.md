# 官方数据库恢复点实现记录

日期：2026-09-13。任务分支：`task/official-db-restore`。基线：`b8374945`。本任务为本地实现，正式版本仍是 `rq0.92.2`；没有改动发布标签、附件或正式 dist。

## 目标与根因

数据库保存剧情事件、人物长期记忆、承诺伏笔、社交轨迹和纪要。回档成功意味着这些数据属于存活的消息分支，后续正文能够正常召回、RQ 表能够继续写入；数据库失败不应作废已完成的核心游戏结算。

玩家只更新角色卡后出现“缺少回档同步确认接口”，原因是 0.92.2 的确认逻辑依赖额外接口，官方插件没有该接口。更早版本在删楼回放期间写入数据库，又可能覆盖其待恢复记录。单纯延长等待或删除未来行，无法恢复同楼被覆盖、被删除的记忆值。

本实现把恢复历史放在游戏聊天变量中，恢复时调用官方公开的 `importTableAsJson(json, { persist: true })`。玩家继续修改脚本与正则的版本号更新游戏，数据库继续按官方渠道更新。

## 生命周期及影响范围

1. 官方持久填表回调、稳定切聊/启动、即时业务执行前、正文回合开始前，尝试记录当前官方导出。临时楼、跨聊天、未来数据、明确运行态回调和未结算写入不形成有效恢复点。
2. `_rqgy数据库恢复点` 保存首份完整 JSON 及后续差量，每点绑定聊天、楼层、稳定消息/分支身份、官方持久来源和完整性指纹。同楼保留多个版本。150 次追加测试的记录体积低于逐次整表备份的八分之一；这不是所有编辑模式的固定压缩率。
3. `_rqgy数据库恢复锚` 是一个小型版本引用，随正文快照和新即时业务撤回票保存。完整回档可恢复业务前，正文重掷可保留业务后；恢复点本体不复制进每张撤回票。旧票不要求新增字段，数据版本仍为 9。
4. 删楼/重掷先关闭数据库读写，确认目标消息已落位后选择恢复点；切换 swipe 使用严格早于该楼的点。官方持久导入成功、内容回读一致、当前聊天/API/令牌/分支仍匹配，且原有稳定快照门通过，才恢复召回与 RQ 写入。
5. 多个 iframe 共用一项导入任务；挂起时不重复导入。明确失败可间隔至少一秒重试，同一任务最多三次。迟到 SQL 保留原有世代校验与补偿。成功后裁掉未来恢复点并广播更新信号。
6. 迟到回放若重新带入未来楼层，或在持久来源没变时把同楼表内容倒退，重新恢复到保留点。正式手动编辑改变持久来源，应正常保存新版本。
7. 重开只清空五张游戏表的数据，其他导出表保留。通常回档恢复该聊天的完整表导出；不会修改插件全局配置。

直接消费者包括普通正文记忆胶囊、RQ 剧情事件补写、社交轨迹写入、即时业务完整撤回、正文重掷、原生删楼、swipe、切聊、刷新和重开。许曼君剧情选择及其他角色状态机继续沿用基线修复，本任务不更改剧情判定。

## 旧档与失败边界

- 首次接入只从当前有效数据库建立首点，不把当前数据冒充较早楼层。无游戏历史点时，可以读取消息中单一作用域、没有后继增量日志的官方完整快照；遇到日志、多作用域或不完整数据时交给官方回放。
- 已经丢失且没有备份的历史无法保证找回。记录损坏、身份不符、缺少导入能力或回读不一致时，保留恢复记录和失败关闭的数据库门，不伪造恢复成功。
- 明确的聊天保存接口会被等待；保存失败标记为待补存。没有显式保存接口的旧宿主使用聊天变量 API 自带的防抖保存，立即关闭页面仍可能丢失尚未落盘的最后一点。
- 官方持久导入没有取消或固定聊天参数。在实际导入期间，顶层原生模态对话框阻止普通点击切聊和页面快捷键，完成后释放；导入长时间不返回时可刷新页面。不能声称这能阻止第三方脚本/控制台强行切聊，官方 API 内部跨异步边界的聊天归属仍是其能力限制。
- 等待调用超时不会取消已经进入官方内部的导入，也不会提前开放数据库写入。旧聊天、旧令牌、旧分支的迟到返回不能认可当前恢复成功。

## 官方接口依据

检查了官方 `spv9.2.3`（`c99fa5c`）以及 `spv9.2.5.1` 源码。两版 `src/service/table/table-import-service.ts` 的 Git blob 均为 `bea535043d89eb80061063a6141fc65760895274`。持久导入在有历史锚时写入 `data_replace`，无锚时形成完整初始保存，然后刷新运行态和相关输出。`restoreTableAsJson` 仅恢复运行态，不用作本任务的持久恢复。

官方源码没有修改。官方原有导入服务及提交持久化测试 13 项通过，覆盖真实提交保存逻辑（存储 provider 为测试替身）。游戏侧测试使用真实桥代码、真实 SQLite，公开导入传输由测试替身提供。

## 同任务续办：重开完整入口与裂缝保留

### 需求与根因

数据库是可重建的长期记忆，重开应清空旧局五张游戏表，普通回档应恢复目标分支。玩家继续更新游戏脚本与正则版本号，数据库继续使用官方更新；没有修改官方插件或增加其私有接口。本次沿用 6ef02c46 的官方持久导入恢复点实现。

复核完整重开入口后，补齐两个边界：原入口只有末楼 ≥ 1 才标记并等待清表，只有 0 楼时会漏清；API 迟到且新序章已经生成后，恢复端把末楼 > 0 一直理解成删楼尚未结束。现在所有重开都标记清场；恢复端在观察到真正的 0 楼时保存同一令牌的 `重开落位分支`，允许同一 0 楼分支上后续的新序章期间继续清场。该字段属于游戏自己的恢复栅栏，可跨模块重载恢复，并不要求官方确认接口。分支不符、聊天变化、旧令牌、未落到目标楼仍不放行。

裂缝调查原本通过四份线索拼成揭晓物，玩家读信后打开裂缝，供情报显示、阶段入口及后续调查分流使用。旧完整撤回会恢复业务前 stat 并清空晋阶镜像，因此也把已经打开的裂缝关回去。现按用户取舍，普通撤回、回档、正文重掷保留本局已打开裂缝，重开清空全部进度。

### 状态生命周期与保留边界

- 线索生产者覆盖翻垃圾、摄像头调查结算、打听、对饮、朋友圈考古及母亲双拼。碎片先落 MVU，提交后再写镜像；未确认裂缝的碎片仍沿原回退语义，未改成永久资源。
- `读信揭晓` 是裂缝确认生产者，先要求四份线索，再置已确认、归档该角色的揭晓物，核心成功后写镜像。没有新增奖励或重演票。
- 普通镜像清场保留已确认角色的裂缝及四份完成进度；阶段、入住时段和未完成碎片仍清场并从目标数据重建。重开显式全清，并继续作废旧异步镜像写世代。
- `裂缝揭晓状态.ts` 在脚本写回与守护/回档收口处统一已打开状态：四份完成进度、已确认、揭晓物归档一起成立。仅移除该已确认角色的五类专用揭晓物，不影响红酒、衣物、现金等资源，不替玩家创建缺席住户。
- 即时业务完整撤回系统继续负责金钱、物品、冷却、其他角色剧情及聊天快照。读信的原场景票随完整撤回清理；正文重掷继续沿原票重演而不重复结算。没有删除其他角色剧情检查点保护。
- 撤回中途保存失败时，旧票签名与版本保持不变；恢复校验在核对原票完整性、聊天、消息身份、分支后，只额外接受“原业务前数据 + 已打开裂缝”的准确状态。金钱等任何其他差异仍拒绝，避免重复退款或错认其他业务。
- 时间撤销还原旧镜像快照时同样保留已打开裂缝。刷新从现有镜像继续；回档前可读取的旧档确认态会先入镜像。缺少该角色的目标楼不提前创建角色，后续正常入列时才应用保留状态。
