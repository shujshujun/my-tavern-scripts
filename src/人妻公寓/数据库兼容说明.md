# 《人妻公寓》数据库共生说明

数据库插件是可选增强项，不是游戏依赖。没有安装数据库时，地图、回合、手机、经济、背包和角色状态仍正常运行。

## 安装本游戏表

打开游戏手机的“我”页面，点击“安装/更新本游戏表”。游戏只向当前聊天合并四张 `RQ_`
表，保留玩家当前模板中的其他表，不修改数据库的全局模板。

- `RQ_剧情事件`：游戏脚本在回合成功落楼后写入，数据库 AI 不得修改。
- `RQ_人物长期记忆`：保存会影响人物未来反应的长期事实。
- `RQ_承诺与伏笔`：保存待兑现的约定、威胁、欠账、疑点和伏笔。
- `RQ_社交轨迹`：保存有后续意义的微信、朋友圈、邀约和赠礼结果。微信邀约结果、父亲来电结论、当面赠礼结果由游戏脚本用 `RQP-`
  事件键和固定措辞直写。妻子私聊得到有效回复后，游戏可额外调用一次数据库 AI，将上一成功版本与尚未整理的增量压成严格结构化的 `微信进展`。每个当前分支前缀有独立版本键；表里不保存聊天原文，填表 AI 也不得改写这些脚本行。

对应的可手动导入模板是 [人妻公寓数据库模板.json](./人妻公寓数据库模板.json)。手机按钮与该文件使用同一份模板。

## 默认填表规则

数据库按正文 AI 楼层调度，不是玩家每发一条消息就逐表调用：

- `RQ_剧情事件` 的自动填表频率为 `0`，只由游戏脚本在成功回合后写入。
- `RQ_人物长期记忆` 与 `RQ_承诺与伏笔` 共用一组调度：最多回看 12 个未处理 AI 楼层，每累计 3
  层处理一批 3 层。两张表在同一请求中判断，只记录会影响后续的长期事实。
- `RQ_社交轨迹` 使用独立低频组：最多回看 12 个未处理 AI 楼层，每累计 6 层处理一批 6
  层。普通寒暄不入表；微信进展和 `RQP-` 硬事件仍由游戏脚本即时维护。
- 没有重要变化时应输出合法的空更新，不得为了凑长度虚构记录。

正常首试成功时，三张 AI 表合计约每 6 个正文 AI 楼层调用 3 次填表模型；旧配置约为 10
次。点击“安装/更新本游戏表”会保留已有数据行并替换为新调度，不修改其他作者的表。

数据库插件的全局“AI 回复最小长度”不属于表格模板。当前插件同时用它判断正文是否过短和填表模型输出是否过短，默认
`500` 会把合法的简短或空更新误判为“AI回复过短”。建议：

- 将“AI 回复最小长度”设为 `0`。
- 将“填表最大重试”设为 `2`；这里表示总共尝试两次。
- 不要要求模型把空更新填充到 500 字。

游戏会读取公开配置并在首次说明和手机“我”页面显示状态。只有玩家明确确认“一键修复”后，游戏才会把这个数据库全局项设为
`0`；安装表格、启动游戏和打开设置都不会自动修改。由于设为 `0` 也会取消“短正文跳过自动填表”，该操作可能让其他角色卡的短正文增加填表请求。当前公开 API
不能读取或修改最大重试次数，需要玩家在“填表工作台 → 自动更新设置 → 高级参数”中手动确认。

## 建议开启 SQLite 模式

四张 `RQ_` 表都提供了完整 DDL、英文物理字段和中文映射注释，可直接在数据库插件的 SQLite 模式中建立。建议玩家在数据库设置中开启 SQLite：

- 游戏可用参数化 `WHERE`、`ORDER BY`、`LIMIT` 精确读取相关人物的少量记录，不必每次导出并遍历全表。
- 剧情事件和社交轨迹可按稳定业务键执行参数化 UPSERT；`PRIMARY KEY`、`UNIQUE`、`CHECK` 等约束会在数据库层阻止重复或非法记录。
- SQLite 还提供聚合、跨表 `JOIN`、事务和批量写入能力，后续扩展统计或多表联动时可直接使用。

游戏不能替玩家自动切换模式，因为数据库插件没有公开模式切换接口。手机“我”页面会检测 `SELECT 1 AS ok`
是否真实可执行，并提供“打开数据库设置（开启 SQLite）”按钮。未开启、旧版不支持或 SQL 调用失败时，游戏会自动回退
`exportTableAsJson + updateRow/insertRow` 的普通表格路径，旧档仍可继续使用。

核心提示词不会写入 `{[sql ...]}` 或 `{[db ...]}` 这类仅 SQLite 可解析的模板标签，避免玩家临时切回普通模式后把未解析标签发给正文 AI。

## 手机 AI 路由

“自动（数据库优先）”是默认模式：

1. 检测到数据库公开 `callAI` 接口时，由数据库代发手机内容请求。
2. 没有数据库接口时，使用当前正文 API 的 `generateRaw`。
3. 数据库请求已经发出但报错时，默认不再调用正文 API，避免重复请求或重复计费。玩家可以自行开启失败回退。
4. 玩家也可以强制使用数据库、正文 API，或配置独立的 OpenAI 兼容 API。

微信进展整理是单独的可关闭选项。只要开启，它始终调用数据库当前 AI，与“手机内容 API”选择正文或自定义模型无关。通常一次有效妻子回复会产生“回复请求 + 一次摘要请求”；若前一次摘要失败，下一次会把未成功整理的增量一起补上。首次启用时最多回看当前分支最近 24 条有效私聊。原文会作为待整理数据发送给数据库 AI，但不会写入数据库。

数据库 8.4 不允许外部读取 API
Key、URL 或完整预设内容。本游戏只使用其公开受限代理；预设名可手填，留空时使用数据库当前配置。

## 数据权威边界

MVU 始终是硬状态的唯一权威，数据库不会控制地图位置、金钱、背包、服装、道具和角色当前状态。生成正文前，游戏只按本场焦点人物精确筛选少量长期记忆组成“记忆胶囊”，并明确规定与 MVU 冲突时以 MVU 为准。

完整微信原文只持久化在聊天变量 `_微信`，不会进入正文提示词或数据库；只有上述有限增量会临时发送给摘要 AI。数据库只保存不超过 300
字符的严格 JSON 派生数据，并在写入和召回时双重验证字段、长度和指令型内容。普通记忆查询会排除 `微信进展`；只有地图物理位置、赴约或显式事件演员可靠确认对应妻子在场时，脚本才把当前分支的最新有效版本编译成固定格式的私有记忆。姓名只是在正文里被提到，不会取得私聊召回资格。

私聊记忆只用于避免本人遗忘或否认，不要求正文主动提微信，也不会把微信里的计划、请求或角色扮演当成现实已经发生。每条都标明只归玩家与本人知情。

数据库表本身不保证随酒馆删楼同步回滚。脚本会从当前仍存活的 `_微信` 消息前缀导出版本授权：回档、改写、同楼重掷或切换聊天后，旧分支行即使仍在表里也无法注入；回到较早时间线时，则可重新选中当时仍有效的旧版本。剧情事件和其他社交硬事件仍带楼层/稳定业务键，并同时接受数据库插件自身的时间线恢复机制。
