# 玩家反馈：过夜后数据库不召回、不更新——专项排查

日期：2026-09-11
排查基线：当前《人妻公寓》候选工作树（HEAD `81c88728429fb197962a5b4b0bfa075a942ba69e`，描述 `rq0.91.5-2-g81c88728-dirty`）
数据库依赖：`AlbusKen/shujuku@spv9.2.3`，标签对象 `cefea141fa0bafe26f8f625d6534f145c2c54627`，实际提交 `c99fa5c6811fbe23aad523091ad972d82a774f86`

---

## 一、玩家原始现象

日志：

```text
【脚本 | 人妻公寓游戏逻辑】:
[人妻公寓·数据库] 回档至35楼后的数据库重建未在时限内完成；本轮不读取一般长期记忆。
```

玩家随后观察到：

1. 数据库不再召回；
2. 数据库也不再更新；
3. 现象发生在一次“过夜”之后；
4. 怀疑过夜没有在数据库形成记录，导致数据库时间线断裂。

---

## 二、结论

### 2.1 问题是否真实存在

**存在。**

这不是单纯的显示误报。当前代码在数据库回档重建没有通过安全校验时，会主动关闭：

- 一般长期记忆读取；
- 新的数据库写入；
- 依赖同一数据库时间线门的后续整理。

因此玩家看到“既不召回，也不更新”完全符合生产代码的真实行为；它们不是两个独立故障，而是同一个数据库时间线栅栏没有重新开放。

现有专项测试已稳定覆盖该状态：只要回档目标是35楼，而数据库导出中仍存在技术楼层大于35的通用长期记忆或承诺记录，等待会返回失败，两个脚本实例都保持关门。当前专项测试结果：

- `数据库时间线栅栏.test.mjs` + `数据库双实例恢复就绪.test.mjs`：**43/43 通过**；
- 其中 `Future snapshot and swipe without a trusted callback do not open either instance` 明确验证“未来快照存在时，读取与写入均不能重新开放”。

### 2.2 是否因为“过夜没有记录进数据库”

**不是。**

《人妻公寓》的世界时间允许在不新增酒馆消息楼的情况下推进。正常睡眠是同一条时间事务：先生成独立演出草稿，再写入游戏变量和撤销点；它不要求数据库额外创建一条“过夜楼层”。

更重要的是：日志中的“回档至35楼”只会由游戏真正执行 `回档至(35)` 时写入。正常点击“睡到次日早晨”不会调用该函数，也不会生成这条原因。

因此正确因果关系是：

```text
过夜发生
  ≠ 数据库因缺少“过夜记录”自行断裂

实际还有一次明确回档到35楼
  → 游戏冻结数据库读写
  → 数据库插件未能在时限内证明已经回放到35楼
  → 本轮停止召回，后续写入也继续被挡住
```

“过夜”与故障可能相邻，甚至可能间接放大竞态，但它不是因为缺少一条数据库记录。

## 三、游戏侧直接证据

### 3.1 日志原因只能来自真实回档入口

文件：`src/人妻公寓/脚本/游戏逻辑/回合引擎.ts`

- 第4114行：

```ts
标记数据库时间线将变更(楼层, `回档至${楼层}楼`);
```

`回档至` 还会校验目标楼必须小于当前末楼，然后真实删除目标楼后的消息。因此出现“回档至35楼”时，调用发生前聊天中确实存在35楼之后的消息，不是同楼空操作。

当前生产调用链只有：

```text
客户端“撤回”或史册“回档”
  → eventEmit('人妻公寓:回档', 楼层)
  → 游戏逻辑监听
  → 回档至(Number(楼层))
```

正常过夜走的是 `人妻公寓:睡到次日早晨`，与 `人妻公寓:回档`、`人妻公寓:撤销时间推进` 是三条不同事件。

### 3.2 为什么会同时“不召回”和“不更新”

文件：`src/人妻公寓/脚本/游戏逻辑/数据库桥.ts`

- 第1122行：`数据库时间线允许新写(...)`；
- 第1759行：`等待数据库时间线就绪(最长等待毫秒 = 3500)`；
- 第1777行：输出玩家看到的警告；
- 第1787、1795行：超时后继续安排后台恢复。

回档开始时会持久化一个 pending 栅栏。只有数据库导出的四张关键表都不越过被冻结的目标楼层，且异步写入代次、补偿任务和共享完成令牌均一致，才会重新开放。

校验表包括：

- `RQ_剧情事件 / 楼层`；
- `RQ_人物长期记忆 / 最后楼层`；
- `RQ_承诺与伏笔 / 最后楼层`；
- `RQ_社交轨迹 / 最后楼层`。

脚本只能够直接裁剪自己独占的剧情事件和社交轨迹两表；人物长期记忆、承诺与纪要依赖数据库插件从聊天消息中的 checkpoint / 操作日志回放。只要后两类表仍留有大于35楼的数据，游戏就不会冒险继续读写。

### 3.3 单次超过3.5秒与永久卡住需要区分

如果数据库只是历史较长、SQLite重建超过3.5秒，日志可以出现一次，但后台重试成功后会自行开放。这属于“慢但最终恢复”。

如果玩家在此后多个回合持续既不召回也不更新，则不是单纯3.5秒超时，而是至少有一项持续不满足：

- checkpoint 回放失败；
- 回放根在删楼过程中丢失；
- 旧异步填表迟到写回未来状态；
- 数据库导出仍含大于35楼的通用记忆或承诺；
- 插件刷新回调或SQLite重建持续失败。

## 四、`spv9.2.3` 中已确认的删楼竞态

为避免只依据游戏桥推断，本次已把玩家使用的 `shujuku@spv9.2.3` 官方源码按标签取到 `.codex-tmp/player-db-overnight-investigation/shujuku-spv923`，只读核对。

### 4.1 插件删楼重建故意延迟1.2秒

文件：`src/presentation/bootstrap/chat-mutation-scheduler.ts`

- 第25行：

```ts
export const TRAILING_DELAY_MS_ACU = 1200;
```

- `MESSAGE_DELETED` 到达后只先调度，真正的 checkpoint 前移、SQLite reload 和合并刷新在防抖轮次执行。

### 4.2 插件源码明确记录了一条尚未消除的竞态

文件：`src/service/chat/checkpoint-delete-guard.ts` 第21—22行：

```ts
残余竞态（接受并记录）：删楼后调度防抖窗口（1.2s）内若插件恰好完成一次保存，
post-save 同步会先丢弃待恢复产物。
```

机制如下：

1. 插件平时维护一份删除前的 checkpoint 保管库；
2. 宿主删楼后，等待1.2秒再把被删楼携带的回放根嫁接到幸存楼；
3. 但插件每次自身保存成功后，又会以“当前聊天”为权威重建保管库；
4. 若一次数据库保存恰好在删楼后、恢复轮次前完成，当前聊天已经没有被删楼；
5. 保管库先被覆盖，被删楼的 checkpoint 产物就丢失；
6. 随后的恢复轮次看不到可嫁接产物，冷回放可能无法还原35楼状态。

插件注释认为“生成/填表落盘耗时远大于窗口，实际不可达”，但这个判断只讨论一笔从零开始的写入。若删楼发生时数据库填表已经接近落盘结束，它完全可能在接下来的1.2秒内完成。因此该竞态在真实并发时序中并非不可达。

插件测试还明确保留了以下语义：post-save 一旦发生，保管库就以删楼后的聊天为权威，后续恢复不会复活旧 checkpoint。这对插件自身的主动 purge 是正确的，但无法区分“插件主动 purge”与“玩家回档后恰好撞上另一笔插件保存”。

## 五、为什么过夜可能间接放大该竞态

文件：`src/人妻公寓/脚本/游戏逻辑/隔离事件引擎.ts`

- 第281行，普通独立事件调用：

```ts
generateRaw({ ordered_prompts, user_input: 本拍用户输入, should_stream: 是DeepSeek, generation_id: 生成ID })
```

- 第357行，录像带V4独立事件也使用未标记的 `generateRaw`。

正常“睡到次日早晨”是五类独立事件中会请求正文模型生成演出的入口之一。当前请求有专用 `generation_id` 和提示标记，但没有携带 `automatic_trigger: true`。

在 `shujuku@spv9.2.3` 中：

- `GENERATION_STARTED` 会记录生成上下文；
- `GENERATION_ENDED` 只要不是 dry-run、quiet 或 `automatic_trigger`，就会进入自动填表候选；
- `state-manager.ts` 第194—199行明确只有 `params.automatic_trigger` 才跳过自动填表；
- `init.ts` 第535行据此决定是否调用 `handleNewMessageDebounced_ACU`。

因此，只要 TavernHelper 将这次 `generateRaw` 同步为宿主生成事件，过夜的独立演出就可能被数据库误认作一次普通正文生成，并额外启动自动填表/保存。即使后续消息解析因没有新AI楼而跳过，生成上下文和防抖时序仍会进入插件管线；若解析误绑定当前尾部AI楼，还可能真实落盘。

这不会证明“每次过夜都会坏”，但它会形成以下高风险组合：

```text
过夜独立生成
  → 数据库把辅助生成当普通正文候选
  → 数据库填表/保存仍在进行
  → 玩家随后回档到35楼
  → 1.2秒删楼恢复窗口内，旧保存恰好完成
  → post-save 先覆盖 checkpoint 保管库
  → 回档重建无法恢复到35楼
  → 游戏栅栏持续阻断召回与新写
```

所以本次最准确的判断是：

- **过夜不是因为“没写数据库”而导致故障；**
- **过夜的辅助AI请求未标记为后台生成，可能成为竞态的间接触发器；**
- **真正导致全面停摆的是回档后的数据库 checkpoint / 回放没有完成并通过验证。**

目前没有玩家完整日志，尚不能100%证明该玩家命中的就是上述1.2秒竞态；但生产代码、插件源码和现有回归夹具已经证明该故障链真实可达，不能按“玩家误会”关闭。

## 六、建议修复方案

### P0：隔离AI请求必须获得窄范围的后台生成身份

不能用“只要隔离事件进行中，就把所有生成都标为后台”的宽泛方案，因为隔离期间若错误出现一笔真实原生正文，它必须被拒绝而不是被误标。

建议选择以下之一：

1. 验证 TavernHelper 对额外配置字段的透传后，在两个隔离 `generateRaw` 调用上显式加入 `automatic_trigger: true`；
2. 若 `generateRaw` 不稳定透传该字段，则维护“本卡发起的隔离 generation_id”注册表，在最先执行的 `GENERATION_STARTED` 监听中只对匹配ID的请求写入 `automatic_trigger`；
3. 保留现有 `<rqgy_isolated_event_request>` 提示标记作为第二重身份校验，但不要只用全局 `隔离事件进行中()`。

目标：睡眠、监控、健身演出、录像带等辅助生成不触发通用数据库自动填表，也不污染普通正文生成租约。

### P0：补一条“过夜进行中 + 回档”的真实并发回归

测试必须覆盖：

1. 当前末楼35；
2. 发起睡眠独立生成；
3. 数据库自动填表/保存处于即将落盘状态；
4. 再产生36、37楼；
5. 回档至35；
6. 在删楼后1.2秒窗口内完成旧保存；
7. 验证旧 checkpoint 保管库没有被覆盖；
8. 验证四表最大技术楼层均不超过35；
9. 验证一般记忆召回和新写重新开放。

### P1：数据库插件应先保护删楼保管库，再做防抖重建

上游稳妥修法：

- `MESSAGE_DELETED` 到达时立即冻结当前 vault 代次或立即提取 lost artifacts；
- 防抖只延迟昂贵的SQLite reload/UI刷新，不延迟“保护被删 checkpoint”这一步；
- host-delete pending 期间，普通 post-save 不得用删楼后的聊天覆盖该代次的 vault；
- 恢复结束后再以当前聊天重建 vault；
- 插件自身 purge 使用显式 source/token 绕过该保护，不能靠“任何 post-save 都视为主动 purge”区分。

### P1：增强游戏侧诊断，不再只输出笼统超时

警告应至少附带：

- 聊天标识、栅栏令牌与原因；
- 冻结目标楼层、当前聊天末楼；
- 四张关键表各自检测到的最大技术楼层；
- 是否收到可信刷新回调；
- SQLite导出是否成功；
- 脚本独占表裁剪是否成功；
- 是否存在迟到数据库写及补偿状态；
- 当前后台重试次数。

这样下一份玩家日志可以直接区分“只是重建慢”与“checkpoint已经丢失”。

### P2：不要用直接删除通用长期记忆作为第一修复

游戏目前不直接裁剪人物长期记忆和承诺是有意的：某行在36楼被更新前，35楼可能已有旧版本；直接 `DELETE last_floor > 35` 会把旧版本也一起丢掉，无法还原回档前内容。

因此不建议为了快速开门，直接删除所有未来通用记忆。正确方向是恢复/保护插件的消息级 checkpoint，或在插件侧提供可验证的“回放到目标楼”API。

## 八、需要从玩家完整日志核对的关键标记

若取得故障前后完整日志，优先搜索：

```text
ACU MESSAGE_DELETED event detected
[删楼守卫]
[聊天变更] 删楼 checkpoint 前移恢复失败
[SQLite] 聊天变更：数据库重建失败
ACU: Skip auto table update due to quiet/background generation
GENERATION_STARTED
GENERATION_ENDED
TableUpdateCommit
回档至35楼
```

判定方式：

- 只有一次3.5秒警告，随后出现重建完成并恢复写入：慢重建，非永久故障；
- 出现删楼守卫恢复失败/无根/V2 replay失败：checkpoint链问题；
- 过夜生成后出现自动填表，但没有 quiet/background skip：辅助生成身份缺失；
- 回档后仍出现旧 `TableUpdateCommit` 成功：迟到写与删楼竞态；
- 四表中人物长期记忆或承诺最大楼层仍大于35：栅栏持续关门的直接原因。

## 九、最终定级

- 真实性：**确认存在**；
- 严重度：**P1**（数据库长期停摆，但游戏核心MVU状态通常仍可继续）；
- 是否数据安全相关：**是**，当前关门行为本身是在避免把未来分支记忆写进回档后的新分支；
- 直接原因：**回档至35楼后的数据库消息级回放未完成或未通过验证**；
- “过夜没数据库记录”假设：**排除**；
- 过夜关联：**可能通过未标记的辅助生成启动额外填表/保存，间接放大删楼1.2秒竞态**；
- 当前处置：本轮仅专项排查和记录，未修改生产源码、未打包、未发布。
