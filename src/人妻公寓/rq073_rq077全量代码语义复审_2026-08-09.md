### 0.74-001 `MVU解析模式.ts`：变量解析独立路由与版本化初始化

1. **设计初衷**：正文模型只写故事；变量解析只走数据库代发或玩家配置的自定义 API，避免正文与 MVU 双重解析、重复计费和重复写变量。
2. **正常链路**：启动时仅在 MVU 已是外置模式或设置写入成功后记录 0.74 初始化标记；回合读取规范后的 `自动/自定义` 偏好，经纯路由矩阵选择数据库、自定义或明确不可用。
3. **游戏作用**：决定每轮硬状态由谁解析；失败时应保留正文和旧变量并提示配置，不能借正文 API 偷偷补第二次请求。
4. **回归检查**：旧 `正文` 或非法偏好统一规范为 `自动`，不会让设置 UI 无选中态；自动通道不再覆盖现有自定义模型来源；初始化失败不提前写完成标记，允许下次重试。
5. **影响与兼容**：消费者为启动自检、设置页和回合引擎外置解析。数据库不可用、自定义缺配置、旧偏好、写设置失败和双解析互斥已有行为测试。

结论：当前未发现该 0.74 变化遗留的新回归。专项 `MVU外置与二次结算互斥`、`MVU外置解析通道` 共 19 项通过；仍需在后续回合引擎审查中复核迟到解析、取消和时间线切换。

### 0.74-003 `原生正文租约.ts`、`数据库AI租约.ts`：生成所有权与迟到请求

1. **设计初衷**：正文、数据库代发与手机 AI 共用宿主生成资源时必须有明确所有权；不可取消的数据库请求超时后仍要占住租约，直到真实底层请求结束，避免第二次生成重叠。

### 0.77-001 临时回合楼：`refresh:'all'` 转正负载二次回归

1. **设计初衷**：本轮 user/assistant 两条临时楼只有在最终可信正文与变量整表已经写入后才能一起转正；转正必须硬保存并复核，失败时按本轮令牌清理，避免半成品污染历史。
2. **正常链路**：按精确令牌/角色定位两楼并校验 `临时=true`，把两条消息原正文无损写回、保留完整 `extra` 且只将临时标记改为 `false`；有 `saveChat` 时无刷新写入后硬保存，无该接口时走 `refresh:'all'` 保存并重载；重载后再次按令牌/角色复核，成功后才置内存转正并广播回合完成。
3. **游戏作用**：转正是核心提交与数据库记忆、世界书同步、客户端完成事件、手机节拍之间的硬生命周期门。楼务创建/结案状态在转正前已经进入最终整表，因此该门失败会形成“状态已经写入，但客户端仍收到回合失败且没有重拉”的表象；后续推进时间触发重读后，先前楼务才会显示。
4. **BUG 成因**：rq0.77 的回退修复构造纯 `{ message_id, extra }`。酒馆助手真实 `setChatMessages` 只有载荷含 `message` 或 `data` 时才进入 ChatMessage 分支并处理 `extra`；原负载被静默忽略，`refresh:'all'` 保存/重载后仍是 `临时=true`，所以普通房间、普通回合、楼务生成与楼务结案全部在统一复核点报“宿主持久保存后临时标记复核不通过”。原 B6 mock 直接应用 `extra`，没有模拟宿主分派，因而制造了假绿。
5. **影响与兼容**：修复只扩展转正负载，不改变回合顺序、楼务结算或两条持久化路线。正文优先读取真实宿主字段 `mes`，兼容测试/旧对象的 `message`，包括空字符串在内逐字保留；两者都不是字符串时在调用宿主前失败关闭，防止为了触发分派而写坏正文。B4b 用真实分派规则钉住根因，B4c 覆盖缺正文与空正文边界，B6 覆盖旧宿主重载、对象重建、双楼复核和正文不变。

结论：已确认这是 0.77 修复自身引入/遗留的全局回归，并随 rq0.78 修复发布。`临时回合楼生命周期` 33/33，通过；回合失败恢复、楼务微信、管理任务、通知、远程地点门、新手引导隔离、原生/数据库/手机时间线与迟到租约相关回归 65/65，通过；定向 TypeScript 与 `git diff --check` 通过。当前无可用的真实 SillyTavern 浏览器页，因此宿主点击冒烟仍列为发布后人工验收项。

### 0.74-005 监控普通提示：确认删除失败后的事务闭环

1. **设计初衷**：监控点击在调用 `查看摄像头` 前先保存入口事务，使软冷却/待选、核心 stat 与 `_隔离事件/_上次隔离回合/_侦探/_场景` 四键属于同一次原子点击；全部成功才删除事务。
2. **正常链路**：普通提示、已确认或死路先在事务仍存在时执行 `落地`；核心成功且身份仍有效后确认删除事务并保留本次合法 `_侦探`。确认失败时，仍在原聊天且能证明是本事务才恢复入口 MVU 与四键；切聊、损坏记录或他事务绝不猜测写入。
3. **游戏作用**：该事务是硬生命周期，避免一次不产生 AI 正文的监控点击只提交一半。若核心成功而事务未闭合，之后启动恢复会按事务保存的提交前完整 data 退款，可能把故障之后的正常进度一并覆盖。
4. **BUG 成因**：0.74 的 `catch (收口错误)` 仅广播失败，没有立即补偿。单纯在外层调用严格回滚仍不足：`updateVariablesWith` 的 updater 可能已经同步删除事务，宿主 Promise 随后才失败，此时普通回滚会因事务缺失拒绝执行。
5. **影响与兼容**：确认函数新增可选核心恢复回调，并记录本次删除 updater 是否已严格核对并执行。确认失败后只有“当前仍是同一事务”或“本 updater 已执行且键缺失”才补偿；成功路径不调用恢复、继续保留合法软计数。补偿前后发生切聊、事务损坏/替换/并发缺失均失败关闭，原错误与 MVU/chat 补偿错误合并。

结论：当前工作树已修复。动态专项 50/50，通过；侦探、隔离、时间推进/撤销、回合恢复、新手引导、正文幕与荣耀洞相邻回归 68/68，通过；定向 TypeScript 与 `git diff --check` 通过。

### 0.75-002 生成通道：从单向观察门到全所有者闭环

1. **设计初衷**：TavernHelper 实际只有一条共享生成资源；固定 0 楼正文、酒馆原生 normal、手机自动/手动短生成、隔离演出（含楼务剧情）与数据库 `callAI` 必须有唯一可证明的当前 owner。
2. **正常链路**：固定回合在回合锁和首个真实 `await` 前取得前台 token；原生 normal 在 `GENERATION_STARTED` 登记开始票时取得并随 owner 释放；隔离草稿仅在 AI 生成期持前台 token；手机手动批次跨绿/黄/红持外层 token，每次 `小生成` 持可嵌套内层 token。数据库外层超时后底层未 settle 时，四类新 AI 入口都先查全局迟到租约。
3. **游戏作用**：防止两笔 AI 同时争用供应商/宿主生成槽，避免手机或楼务迟到输出与正文临时楼交叉，也避免一次失败后旧 owner 阻塞所有后续回合。
4. **BUG 成因**：0.75 只有“正文开始前读取手机在途布尔”的单向门；正文占槽后手机、原生或隔离仍可反向启动。原生票、隔离 `生成中` 与数据库租约各管各的身份，没有统一生成槽 owner；固定回合 `finally` 又先广播失败、后释放 token，同步重试会被旧 token 拒绝，监听器异常还能造成泄漏。
5. **影响与兼容**：共享模块是无宿主依赖的纯 token 状态机；前台至多一个、手机 token 可嵌套、释放幂等，失败取得不返回假租约。不禁止阅读手机；只有手动首条消息尚未写库时会在正文占槽下给可见拒绝。被拒原生请求只在聊天 ID、时间线世代、user 楼层、对象引用仍一致且当前无任何原生票时延迟停止；硬停止先安排，失败提示后广播，提示监听器异常不再阻断收口。

结论：R-004 已在当前工作树闭环。专项 8 个相关测试文件 119/119 通过；原生拒绝顺序与无票守卫补充专项 37/37 通过；全量回归、六套定向 TypeScript、15 个当前变更 TS/MJS 的 ESLint 与 `git diff --check` 全部通过。`约出来` 在写邀约与实际 `小生成` 之间仍可能因新正文启动而得到本地兜底回复，但不会并发调用 AI、不会破坏事务，保留为低风险体验项而非本轮硬生命周期缺陷。
