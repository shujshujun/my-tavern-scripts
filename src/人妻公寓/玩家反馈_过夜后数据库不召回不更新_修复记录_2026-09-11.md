# 玩家反馈：过夜后数据库不召回、不更新——修复记录

日期：2026-09-11
状态：**游戏侧已修复并留在 0.91.6 累积工作树；未组卡、未打标签、未推送、未发布。**

## 一、玩家现象

玩家在过夜后看到：

```text
【脚本 | 人妻公寓游戏逻辑】:
[人妻公寓·数据库] 回档至35楼后的数据库重建未在时限内完成；本轮不读取一般长期记忆。
```

随后数据库同时出现：

- 一般长期记忆不再召回；
- 新的剧情事件、社交轨迹及通用填表不再更新。

## 二、最终根因结论

这不是“过夜没有单独写一条数据库记录”造成的。

正常睡眠只推进世界绝对时段，可以不新增酒馆正文楼；数据库本来也不要求每次睡眠独立建行。日志中的“回档至35楼”说明过夜流程附近又发生了真实删楼／回档，数据库时间线栅栏因此进入恢复态。在数据库插件尚未证明四张游戏表已经退回目标楼层前，游戏会故意同时关闭一般长期记忆读取和新写入，防止未来分支记忆污染当前时间线。

游戏侧确认的可触发链为：

```text
睡眠／监控／荣耀洞／录像带等隔离演出
→ 使用 TavernHelper.generateRaw 生成前台可取消正文草稿
→ 酒馆助手广播 normal GENERATION_AFTER_COMMANDS
→ 数据库插件可能把它误认成普通玩家正文生成
→ 启动剧情规划、初始 checkpoint 或纪要索引等数据库工作
→ 若此类数据库保存尚在收尾时紧接着发生回档
→ 更容易撞入 shujuku@spv9.2.3 的删楼 checkpoint 保管库竞态
→ 数据库恢复无法在有界时间内完成
→ 游戏安全栅栏持续关闭召回和新写入
```

因此，本次修复目标不是放宽数据库恢复门，也不是粗暴删除未来楼层长期记忆，而是让游戏脚本自己的隔离 AI 演出在数据库处理器看来具有正确的“辅助／后台生成”身份，从源头消除这条额外数据库写入链。

## 三、关键运行时核对

### 3.1 直接给 `generateRaw` 配置加字段是无效方案

最初候选方案曾考虑：

```ts
generateRaw({
  ...,
  automatic_trigger: true,
});
```

但对当前酒馆助手真实源码核对后确认，这种写法在运行时不会生效。

核对源码：

```text
D:/SillyTavern/codex-tmp-js-slash-runner/src/function/generate/index.ts
```

其中 `fromGenerateRawConfig()` 只把声明过的字段转换到内部参数，未知的 `automatic_trigger` 会被丢弃；随后 `iframeGenerate()` 固定广播：

```ts
await eventSource.emit(event_types.GENERATION_AFTER_COMMANDS, 'normal', {}, false);
```

也就是说，数据库插件真正收到的是这个新建的空 `options` 对象，而不是调用方传给 `generateRaw` 的原配置对象。仅在请求配置里写字段会形成“单元测试看似通过、真实宿主完全无效”的假修复。本次最终代码没有保留该错误方案。

### 3.2 数据库插件实际认可的跳过条件

核对 `shujuku@spv9.2.3` 源码：

```text
D:/SillyTavern/codex-tmp-shujuku-audit/src/presentation/bootstrap/init.ts
D:/SillyTavern/codex-tmp-shujuku-audit/src/service/runtime/state-manager.ts
```

其 `GENERATION_AFTER_COMMANDS` 处理与状态判定明确把以下请求排除在普通剧情规划、初始 checkpoint、纪要索引／自动处理之外：

- `dryRun`；
- quiet 请求；
- `params.automatic_trigger === true`。

所以真正有效的接线必须在数据库监听器运行前，修改酒馆助手广播时所携带的**同一个事件 options 对象**。

## 四、实际修复

### 4.1 新增通用辅助生成事件标记

文件：

```text
src/人妻公寓/脚本/游戏逻辑/数据库辅助生成标记.ts
```

新增：

```ts
export function 标记脚本辅助生成事件(
  类型: unknown,
  选项: unknown,
  dryRun = false,
): boolean
```

语义：

- 只接受真实 `normal`、非 `dryRun` 请求；
- 在可写的事件 options 对象上设置 `automatic_trigger = true`；
- 参数损坏、对象冻结或无法写入时返回 `false`，不得假装已建立身份；
- 与既有“临时回合楼阻止提前填表”逻辑复用同一安全写入函数，避免两套实现分叉。

### 4.2 隔离生成紧贴 `generateRaw` 注册一次性队首监听

文件：

```text
src/人妻公寓/脚本/游戏逻辑/隔离事件引擎.ts
```

新增私有入口：

```ts
注册隔离辅助生成事件标记()
```

每次隔离 AI 请求都会按以下顺序执行：

```text
取得既有共享前台生成租约
→ eventMakeFirst(GENERATION_AFTER_COMMANDS) 注册一次性队首监听
→ 调用 generateRaw
→ 酒馆助手广播 normal GENERATION_AFTER_COMMANDS
→ 游戏监听先把同一 options 对象标记 automatic_trigger=true
→ 监听立即自卸载
→ 数据库插件后续监听读取到后台身份并跳过普通填表链
```

如果事件对象不可写，游戏会在 AI 真正发出前失败关闭并提示：

```text
无法建立辅助生成身份；为避免数据库误填表，本次独立演出没有启动。
```

这比继续生成、再让数据库误认领更安全。

所有异常和结束路径都会在 `finally` 再次幂等卸载未消费监听，避免下一次无关生成被误标。

### 4.3 覆盖范围

普通隔离入口统一经过 `生成隔离事件草稿`，因此修复覆盖：

- 睡到次日早晨的独立演出；
- 监控；
- 荣耀洞；
- 母亲视频通话等同族隔离生成。

录像带 V4 使用独立生成函数，本次也同步接入同一事件身份门。

### 4.4 保留的既有行为

本修复没有把请求改成 `should_silence: true`，因此：

- 酒馆停止按钮仍能终止前台隔离生成；
- 游戏内取消入口仍能立即结束本地等待并释放前台租约；
- 每次点击仍只发一次正文 API 请求；
- 没有改用数据库 AI；
- 没有新增第二次生成或失败自动重试；
- 睡眠的时间、奖励、撤销点仍只在草稿成功后原子提交。

## 五、五问语义复核

### 1. 设计初衷

隔离演出是游戏脚本主动发起、不会创建宿主正文楼的前台可取消辅助生成。它可以提供睡眠、监控和录像带正文，但不应被数据库当成一次新的玩家正式正文回合。

### 2. 正常运行

游戏在调用 `generateRaw` 前临时取得一次 `GENERATION_AFTER_COMMANDS` 队首监听，只标记紧接着发生的那个 normal 请求；事件被认领后立刻卸载，调用完成或失败时再由 `finally` 兜底卸载。

### 3. 游戏作用与影响

数据库不再因为过夜等隔离演出额外启动普通填表、剧情规划或 checkpoint 写入，降低随后回档时撞上迟到数据库保存、导致恢复栅栏长期关闭的概率。隔离正文、时间结算、取消和历史记录本身保持原功能。

### 4. 根因链

旧实现：无宿主正文楼的 `generateRaw` 仍广播 normal 生成事件 → 数据库认为是普通正文 → 发起可迟到的数据库工作 → 紧接回档时与删楼 checkpoint 恢复竞争 → 栅栏无法证明已经退回目标楼 → 召回与写入一起关闭。

同时，简单在 `generateRaw` 入参增加 `automatic_trigger` 会被 TavernHelper 配置转换层丢弃，不能修复真实运行环境。

### 5. 修复边界与兼容

只校正脚本自有隔离生成的数据库身份，不修改数据库安全栅栏、楼层边界、SQLite 表内容、聊天 checkpoint 或 MVU 真值。真实玩家正文仍按原规则触发数据库；真实回档仍必须通过四表楼层与稳定快照验证。
