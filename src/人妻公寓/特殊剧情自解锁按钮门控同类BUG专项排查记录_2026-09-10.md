## 一、玩家反馈与已确认根因

玩家反馈周小满《不再留门》来到 A5「这次，让他自己看」第 3/3 拍后，画面显示：

- `明确回应她的决定`
- `暂缓，保留当前进度`

但点击没有生成、没有状态变化，也没有可见错误提示。

根因已经确认在客户端按钮到脚本监听器之间，不在《不再留门》后端状态机：

1. `App.vue` 把 `场景操作锁` 作为 `useRoomActions` 的 `发送中` 参数传入：

   ```ts
   场景操作锁 = 发送中 || 场景剧情锁定 || 界面事务提交中
   ```

2. `useRoomActions.ts` 中《不再留门》房内动作回调会先检查 `!发送中.value`。当前恰好处于需要玩家回应的场景剧情锁，所以回调静默停止，业务事件根本没有发出。

3. 独立的 `不再留门进展.vue` 虽然直接显示了决定按钮，但它最终仍调用 `App.vue` 的 `请求不再留门动作()`。该函数通过：

   ```ts
   提交界面事务(() => eventEmit('人妻公寓:不再留门动作', 动作))
   ```

   提交，而 `提交界面事务()` 默认不允许穿过 `场景剧情锁定`。调用没有传入 `允许场景剧情锁=true`，因此第二条入口也静默失败。

4. `不再留门系统.ts` 本身有意在本线当前剧情票存在时提供 `确认当前决定`、`暂缓`，并对 A5/A7/A9 生成严格的明确回应文本；`index.ts` 的监听器收到事件后也能进入真实 `执行回合()`。故障是事件没有抵达监听器。

这是一个典型的“**用来解除当前锁的按钮，又被当前锁本身拦住**”的自锁问题。

## 二、同类问题的判定口径

本次不把所有“剧情期间按钮不可点击”都算成同一个 BUG，只认以下完整条件：

1. 某条特殊剧情已经拥有当前前台锁或专属硬现场；
2. 该剧情还需要一个结构化按钮来确认、暂缓、停止、恢复或完成当前锁；
3. 按钮在界面上仍然可见或业务上必须可用；
4. 按钮经过通用 `场景剧情锁定`、被复用为 `发送中` 的组合锁，或默认 `提交界面事务` 门；
5. 因为当前剧情自己的锁而不能把意图送到唯一后端所有者；
6. 没有另一条明确、可见且符合设计的主推进路径，或者界面展示了会静默失效的重复按钮。

据此区分三类结果：

- **阻断型同类 BUG**：玩家无法通过设计中的主入口继续。
- **非阻断型同源死按钮**：主推进路径仍可用，但另一个可见按钮因同一门控原理静默失效。
- **相邻 UI 不一致**：动作数量、动作数组、抽屉显示和锁定状态不一致，但不阻断该路线的唯一进度。

## 三、五问结论

### 1. 玩家真正期待什么

剧情锁定时，普通地图、商店、其他路线和无关房内操作应暂停；但负责当前剧情本身的“回应、暂缓、停止、恢复、最后现实动作”必须仍可操作，并且点击后要么提交，要么明确提示失败原因，不能静默无反应。

### 2. 正常数据流应是什么

```text
当前剧情状态
→ 只生成本线合法控制按钮
→ 客户端只允许该按钮穿过本线自己的锁
→ eventEmit
→ index.ts 唯一监听器二次复核地点／票据／世代
→ 状态机或真实回合提交
→ MVU 持久化
→ 界面刷新
```

不能把“允许本线当前控制按钮”实现为“放开所有场景锁”，也不能只解除前端一层而忽略后端的地点、时段、票据和重复提交校验。

### 3. 必须保持的事实与不变量

- 其他路线、商店、地图、手机、背包和普通房内动作继续被强剧情锁定。
- 生成中、MVU 保存中、移动中和重复点击继续禁止。
- 只有本线当前票据真正处于前台时，才可放行本线控制按钮。
- 迟到按钮必须由后端重新校验并失败关闭，不能复活旧票。
- 暂缓、撤回、停止不能误吞道具、照片、母带、钥匙或已成立生活事实。
- 不能把“按钮能点”变成并行启动第二个剧情回合。

### 4. 当前实现为什么偏离

客户端把多个含义不同的状态合并进 `场景操作锁`，又把这个组合锁以名为 `发送中` 的参数交给房内动作层。结果是业务回调无法区分：

- 真正正在生成；
- 正在保存；
- 当前路线自己的强剧情锁；
- 其他路线的强剧情锁。

同时，`提交界面事务` 的例外是逐调用点传入布尔值，没有统一的“当前锁所有者／允许动作”契约。《双重继承》最终钥匙和录像带 V4 已显式处理例外，《不再留门》漏接了这套语义。

### 5. 修复边界与兼容要求

- 只对白名单中的《不再留门》当前控制动作放行，并复核确实是本线前台票。
- 不应把所有《不再留门》动作、所有房内动作或所有 `提交界面事务` 统一改成允许穿锁。
- 不应把许曼君《离婚》的重复起场按钮也放行；那里应隐藏重复按钮，而不是允许再次启动同一拍。
- 应统一修正“动作数组非空但动作计数为 0”的抽屉展示逻辑，避免玩家看到死按钮。

## 四、全局客户端门控结构

### 4.1 通用锁

`App.vue` 当前主要相关派生为：

```ts
场景剧情锁定 =
  普通场景剧情功能锁 ||
  录像带前置中 ||
  录像带V4活动 ||
  母亲视频终幕已接通 ||
  双重继承最终收束锁

场景操作锁 = 发送中 || 场景剧情锁定 || 界面事务提交中
```

`提交界面事务(任务, 允许场景剧情锁 = false)` 在以下任一状态会拒绝：

- 正文正在发送／生成；
- 已有界面事务正在提交；
- 当前场景剧情锁定且调用点没有显式放行；
- 场景移动中；
- MVU 操作正在保存。

### 4.2 已经正确实现的例外

当前代码中存在几处正确的正面参考：

- 通用“继续场景剧情”入口使用 `提交界面事务(..., true)`；
- 录像带 V4 的开始、切房、下一幕、完成与安全退出使用专属控制，并显式允许穿过自己的锁；
- 《双重继承》最终 `归位总钥匙` 同时在房间动作回调和 `提交界面事务` 两层做了精确例外，而且仍由后端复核最终收束资格。

这证明项目已有“只允许锁所有者完成自己的最后动作”的设计范式；《不再留门》是漏接，不需要发明一套完全不同的机制。

## 六、确认的其他同源问题

### 6.1 许曼君《离婚》：可出现不阻断主流程的重复死按钮

`许曼君离婚系统.ts` 为了允许剧情提交端识别自己的票，定义了：

```ts
function 自有剧情票(text: string): boolean {
  return String(text ?? '').includes('【许曼君离婚提交:');
}

function 普通强剧情冲突(data, location): boolean {
  return 有地点动作剧情冲突(data, location, 自有剧情票);
}
```

这一规则被地点动作候选也复用了。部分《离婚》剧情动作在正文成功前不改变路线阶段，因此本线票正在前台时，地点动作提供器仍可能重复返回刚才的起场瓷砖。

与此同时：

- `App.vue` 在场景锁期间把 `可见房内动作数` 强制计算为 `0`；
- 但 `普通房间动作` 数组没有同步清空；
- `RoomActionsDrawer` 没有把普通场景锁本身列入 `suppressed`；
- 抽屉可出现“房内操作 · 0项”，手动展开后仍可能看到动作数组中的重复瓷砖；
- 点击后又因 `useRoomActions` 收到的是 `场景操作锁` 而静默停止。

这与《不再留门》拥有相同的前端门控根源，但严重程度不同：

- 《离婚》的当前拍仍由上方通用“剧情待处理”卡和输入框继续；
- 重复瓷砖不是合法的当前解锁按钮，本就不应继续显示；
- 因此它是**非阻断型同源死按钮／重复入口污染**，正确修法是隐藏重复动作或统一抑制抽屉，不是允许它穿锁重新起场。

### 6.2 全局“房内操作 · 0项”与真实动作数组不一致

当前 `可见房内动作数` 在普通场景锁定时统一归零，但 `RoomActionsDrawer` 的 `actions` 仍来自未统一过滤的 `普通房间动作`。这会形成：

```text
计数 = 0
动作数组 = 非空
抽屉未被场景锁抑制
动作回调又被场景操作锁拦截
```

结果是多个路线在无关强剧情期间都可能留下陈旧、无法执行的房内动作。它通常不阻断当前剧情，但会造成：

- “0项”却能展开出按钮；
- 按钮看起来可点，实际无反应；
- 玩家难以判断是剧情要求、保存中，还是程序失效；
- 后续新增真正需要穿锁的按钮时，很容易复发《不再留门》式死锁。

应把这个问题作为独立的客户端动作可见性一致性修复，与《不再留门》业务白名单修复一起回归，但不要用一个粗暴的全局放行解决。

## 七、未发现阻断型同类 BUG 的路线说明

### 7.1 《第二机位》《回国》《双重继承》的普通多拍

这些路线的多拍正文都使用场景剧情事务：

- 第 1 拍由地点动作启动；
- 后续拍进入通用剧情待处理卡；
- 需要玩家回应的拍使用输入框；
- 不需要回应的拍使用专用“继续场景剧情”按钮；
- 该按钮已经显式允许穿过场景锁。

路线自己的地点动作在当前票存在时被冲突检查隐藏，不承担自解锁职责，因此没有《不再留门》的双入口冲突。

### 7.2 安若妍 H7 与《换掉》硬动作

《不必停》H7 的“继续／停下”确实是结构化硬决定，但状态切换顺序是：

1. H7当前剧情票先提交；
2. 路线才进入 `待H7决定`；
3. 通用场景票已经清除；
4. `前台硬决策中` 接管界面并强制展开房内抽屉；
5. 两个按钮不再处于 `场景剧情锁定` 下。

《换掉》的 P1/P2 和换照动作采用相同的“先结束剧情票，再开放硬操作”分层。当前实现可达。

但这是需要测试保护的时序不变量：若以后把“待决定”提前写在票仍存在时，现有 `场景操作锁` 会重新造成自锁。

### 7.3 《分居》的含糊回答与暂缓

《分居》不是在同一锁上显示确认按钮，而是：

- 本拍正文照常提交；
- 若玩家回答含糊或暂缓，保存已经成立的人物决定；
- 把路线留在可重答断点；
- 清掉旧活动票；
- 玩家之后通过新的地点动作重新建立一张票。

因此重答入口与旧票不并存，不存在同类自锁。

### 7.4 录像带、静音会议、母亲视频与荣耀洞

这些大型现场没有复用普通房内动作作为唯一控制器：

- 旧录像带和 V4 有专属控制组件；
- 静音会议有专属交互与散会状态机；
- 母亲视频的接听、回复、结束、重试和继续终幕由手机壳直接控制；
- 荣耀洞用独立拍号和普通输入／离场恢复处理。

它们的控制权和普通场景抽屉分离，本轮没有发现同类自锁。

## 九、建议修复顺序

### P0：修复《不再留门》阻断型自锁

只对白名单动作处理：

- `确认当前决定`
- `暂缓`
- 合法状态下的 `撤回许可`

建议同时满足：

1. 当前前台票确实属于本次 `_不再留门.实例`；
2. 当前地点符合该票目标；
3. 后端 `不再留门动作阻断()` 仍返回可执行；
4. 不是正文生成中、移动中、MVU保存中或重复提交中；
5. 仅对本线自己的场景锁放行。

前端两层都要处理：

- `useRoomActions` 不能再把当前本线锁误当成真正的“正在发送”；
- `请求不再留门动作` 调用 `提交界面事务` 时，必须根据精确动作和当前本线票决定是否允许穿锁。

只改其中一层仍会继续无反应。

### P1：统一抽屉动作、计数和抑制

选择一种唯一语义：

- 场景锁期间普通抽屉整体隐藏，只把真正的锁所有者控制按钮放进独立决策区；或
- 场景锁期间先按“可穿锁动作白名单”过滤动作数组，再由同一个过滤结果同时计算动作数和渲染内容。

不能继续让 `action-count=0` 与非空 `actions` 并存。

### P1：清理《离婚》自有票期间的重复地点动作

《离婚》的“提交端忽略自己的票”和“候选端忽略自己的票”应分开：

- 提交当前票时允许识别同一票；
- 地点动作候选在自有票活动／同地等待期间不重复提供起场瓷砖；
- 当前拍仍只由通用剧情卡继续。

禁止简单把《离婚》所有动作加入穿锁白名单，否则会产生重复生成和双重提交风险。

### P2：补全真实客户端回归

至少覆盖：

1. 《不再留门》A5第3拍点击确认，事件真实到达并进入下一阶段；
2. A5点击暂缓，保留照片与进度；
3. A7第2拍确认开录；
4. A9第2拍确认保留；
5. 合法撤回许可；
6. 生成中、保存中、移动中、错地点、旧票和其他路线票仍拒绝；
7. 《离婚》自有票期间不显示重复起场瓷砖；
8. 抽屉计数和实际按钮数量一致；
9. 《双重继承》最终钥匙与录像带 V4 的现有合法穿锁不回归；
10. 安若妍 H7 在票已消费后仍能选择，票未消费的非法构造不得放行。

推荐把“当前锁所有者是否允许某动作”抽成纯函数并做矩阵测试，再补一条挂载客户端组件的点击接线测试。只做后端状态机测试不足以覆盖本次问题。

## 十、最终结论

1. **确认存在 1 组阻断型同类 BUG：周小满《不再留门》。** A5、A7、A9的明确回应，以及当前票上的暂缓／相关撤回入口都处于风险范围。截图中的 A5 第3拍已经真实复现。
2. **确认存在 1 组非阻断型同源死按钮：许曼君《离婚》。** 自有票期间可能重复显示旧地点动作；点击会被同一客户端组合锁静默拦截，但通用剧情卡仍可继续，所以不是当前主线死锁。
3. **确认存在 1 个全局相邻 UI 缺陷：**场景锁期间动作计数被强制归零，但动作数组与抽屉没有统一过滤，可能出现“房内操作 · 0项”却仍能展开陈旧死按钮。
4. 《第二机位》《不必停》《换掉》《分居》《离婚后日常》《家庭计划》《回国》《双重继承》《302共居》《孕产》《借种》、旧／V4录像带、静音会议、母亲视频终幕、荣耀洞及通用阶段剧情中，**本轮没有发现第二个会阻断唯一主推进路径的同类自锁**。
5. 《双重继承》最终钥匙与录像带 V4 已正确实现“锁所有者精确穿锁”，应作为《不再留门》修复的参考，不应改成全局解锁。
