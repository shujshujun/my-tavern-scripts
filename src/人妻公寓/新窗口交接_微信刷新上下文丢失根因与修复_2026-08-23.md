# 新窗口交接：微信刷新后聊天记录/上下文丢失 —— 根因、已落地修复与剩余待办（2026-08-23）

> 交接对象：Codex（或下一个新窗口）。本文件保留 2026-08-23 当时的完整排查记录；
> **但其中“不是没落盘／锚签名是唯一根因”的结论已被 2026-08-25 实证推翻。请先读下面纠正，
> 再把后文当作历史背景，不得继续沿后文旧结论重复修补。**

## 2026-08-25 最终纠正（优先级最高）

### 真正导致“多版本修了仍复现”的缺口

`mes`／`swipe_id` 等锚签名兼容问题确实存在，旧修复也确实有价值；但它们不是玩家持续复现的
唯一根因。重新读取本机 SillyTavern 与 Tavern Helper 源码后确认：

1. Tavern Helper 的 chat 变量写入先修改内存中的 `chat_metadata.variables`，再走防抖保存；
2. 游戏所谓“硬保存”调用 `await saveMetadata()`；
3. SillyTavern 的 `saveMetadata()` 最终进入 `saveChatConditional()`，保存占用超过约 1 秒时会
   **记录日志后直接 return，不抛错**；实际 `saveChat()` 的网络／完整性失败也会被内部捕获；
4. 因而游戏看到 Promise 正常结束，只能证明“宿主保存函数返回了”，不能证明 `_微信` 已经落盘；
5. 此时气泡已经在内存中显示。玩家立刻刷新后，宿主重新载入较旧的 `_微信`，聊天记录、最近上下文、
   私聊节拍水位一起倒退；节拍引擎随后把该角色判断成“从未联系”，于是又发送初始式对话。

这也解释了为什么此前每一版都“看似修好、自动测试通过、玩家仍复现”：旧测试只断言调用了
`saveMetadata()`，实际上把“函数 resolve”错误等同于“磁盘保存成功”。

### 2026-08-25 已落地的新方向

不再把宿主保存当成唯一保险，而是增加同聊天、同时间线的完整微信恢复层：

- `_微信` 每次权威事务取得单调修订号；
- 请求宿主保存前，同步写入父窗口内存与同一标签页 `sessionStorage`；
- 4.5 秒静默期再合并补存一次宿主，避开正文／变量任务占用窗口；
- 游戏启动先等待真实聊天楼轴，再恢复较新的完整 `_微信`，之后才挂节拍和业务监听；
- 恢复副本绑定 `metadata.integrity + chat ID + 锚楼 + 世界时段 + 稳定分支指纹`；
  正常刷新、正文改写和正常加楼可恢复，回档、删楼、真实 swipe、切聊天则拒绝旧副本；
- 重开一局使用高修订清空墓碑，时间撤销／失败补偿会重新声明当前快照为权威，避免旧副本复活。

主要实现：

- `脚本/游戏逻辑/手机/刷新恢复镜像.ts`
- `脚本/游戏逻辑/手机/数据层.ts`
- `脚本/游戏逻辑/index.ts`
- `脚本/游戏逻辑/回合引擎.ts`
- `tests/人妻公寓/微信刷新恢复镜像.test.mjs`
- `tests/人妻公寓/微信刷新持久化.test.mjs`

验证：刷新恢复两组 19／19；手机、回档、撤销、分支隔离、并发等关联回归 140／140；
定向 ESLint 0 告警；TypeScript 在 `src/人妻公寓` 范围内无新增错误；`git diff --check` 无格式错误。
尚缺的是正式发布构建后的真人宿主刷新验收，不能用自动测试替代这一项。

## 零、2026-08-23 当时的一句话结论（现仅作历史记录）

微信记录**没有丢**，是被 `锚签名` 分支比对**误判为旧分支后整段过滤掉**了。根因是签名把整段正文
`message.mes` 当作分支身份字段，而 SillyTavern 在**同一分支内**就会合法改写 `mes`（宏重新展开、
思维链剥离回写、楼层编辑）。签名一旦失配，该楼产生的全部微信记录不可见；
同时带稳定键的楼务通知因“活键集合”从可见记录重建而丢键，幂等门失效 → 楼务重新派发。

这解释了玩家报的两个现象是**同一个根因**：

1. 刷新酒馆后微信聊天记录、上下文消失；
2. 微信上下文丢失后，夏乔**再一次**触发开局新手指引的修水管楼务。

## 三、v0.86 已修过什么（用户所说“之前已修复”的真实内容）

三处改动都在 `rq0.86` 首次出现，`rq0.87/0.88/0.89` 一直保留。已用
`git show <tag>:<file> | grep -c` 逐标签核对过，`rq0.83/0.84/0.85` 均为 0 处。

1. **事务边界硬保存**（`手机/数据层.ts:395`，4 处调用点）
   新增 `立即持久保存手机聊天变量`，在玩家发送、整批 AI 回复、邀约、撤回、父亲通话、自动节拍、
   冷落预警、实时已读等边界串行调用宿主 `saveMetadata`。
   动机：酒馆助手写 chat 变量只调 `saveMetadataDebounced()`
   （已核对 `codex-tmp-js-slash-runner/src/function/variables.ts:155`），防抖没触发就刷新 = 没落盘。
2. **冷启动楼轴门**（`手机/运行时上下文.ts:32`）
   新增 `手机楼轴已就绪`。手机壳 iframe 可能早于 `SillyTavern.chat` 恢复；空数组会让高楼层记录被当成
   未来数据、带锚记录被当成旧分支，整屏假清空。未就绪时显示“正在恢复微信记录”并短轮询复查，不读库。
3. **swipe_id 归一**（`手机时间线租约.ts:33` `规范手机锚swipeId`）
   把 `undefined`/`null` 与 `0` 视作同一个“尚未发生真实 swipe 的首分支”。
   其原注释已明确写出这条失效路径：旧版把 `undefined` 序列化成 `null`，刷新后宿主 `ensureSwipes`
   补成 `0`，不能因此把同一分支的全部微信误判为旧分支。

**关键判断**：第 3 项与本次 bug 是**同一个 bug**。签名六个字段里刷新会改写的不止 `swipe_id`，
但那次兼容只覆盖了 `swipe_id` 一格，`mes` 从未被保护。所以这不是“修复失效/复发”，
而是**同一处修复没有修完的剩余部分**。

## 四、根因论证（含反向验证）

### 4.1 宿主会在同一分支内改写 `mes` —— 已在 SillyTavern 源码中定位

工作副本：`D:\SillyTavern\SillyTavern-Launcher\SillyTavern`

| 改写点 | 位置 | 触发时机 |
| --- | --- | --- |
| `chat[0].mes = substituteParams(chat[0].mes)` | `public/script.js:4431` | **每次**生成前重新展开开局楼宏（`{{user}}` 等） |
| `message.mes = parsedReasoning.content` | `public/scripts/reasoning.js:1561` | `MESSAGE_RECEIVED`/`MESSAGE_UPDATED` 时把 reasoning 段从 `mes` 剥离回写 |
| `mes.mes = text` | `public/script.js:8119` | 玩家手动编辑楼层正文（随后 `ensureSwipes` + 写回 swipes） |
| `targetMessage.swipes[swipe_id] = targetMessage.mes` | `public/script.js:6874` `syncMesToSwipe` | 只把已经改写的 `mes` 同步进当前 swipe，本身不改 `mes`，不构成签名失配来源 |
| `message.force_avatar` / `mes.name` 重写 | `public/scripts/personas.js:1864` | 切换 persona 时批量改写用户楼（此项影响 `[4]`/`[5]`，属于真实身份变化，**应当**隔离） |

以上前三项都不是 swipe，属于同一分支内的合法改写；第四项只负责同步改写结果。

### 4.2 失配后为什么会“重复派发楼务”

`写库增量`（`数据层.ts:650`）的活键集合是从**过滤后仍存活**的消息重建的：

```ts
const 活消息键 = new Set(新鲜.消息.filter(消息 => 消息.楼 <= 当前楼 && 消息.键).map(...));
```

`同步管理任务微信`（`手机/通知桥.ts:157`）同样用 `读库()` 结果构造 `已有键`。
签名失配 → 旧消息不可见 → 键不在集合里 → 幂等门失效 → 同一楼务事件键重新派发。
这正是“夏乔再一次触发修水管新手指引”的机制。

### 4.3 现场存档验证（重要：本机存档目前是“匹配”的）

用 Python 逐字段比对了本机三个真实存档
（`SillyTavern-Launcher/SillyTavern/data/default-user/chats/人妻公寓*/*.jsonl`）：
9 条记录**全部匹配、全部可见**。

这说明：**本机存档不是复现现场**。它们是 08-03／08-04 的早期短档，
未经历宏重新展开（开局楼 0 未产生微信记录）、未开思维链、未编辑楼层。
因此本机存档只能证明“修复不破坏正常匹配”，**不能**作为复现证据。

同时确认了一个重要细节：这些存档里 `锚签名[1]` 嵌着**完整的第 3 楼正文**（987 字符），
证实了“整段正文进入签名”的设计事实。这也顺带说明签名体积会随正文膨胀。

### 4.4 玩家提供的真实现场日志（2026-08-23 补充，**这是唯一的生产复现证据**）

玩家提供了一段酒馆控制台日志（`C:\Users\Administrator\Downloads\message (1).txt`，
一次沈静仪私聊生成的完整 Chat Completion 请求／响应）。它比本机存档有力得多，
因为它就是失配发生时的提示词快照。

私聊提示词由 `手机/节拍引擎.ts:432` 拼装，其中两个记忆块的数据来源截然不同：

| 记忆块 | 来源 | 是否经过锚签名过滤 | 日志中是否存在 |
| --- | --- | --- | --- |
| `最近本人私聊` | 微信库 `_微信.消息` 最近 12 条 | **是**（`读库()` → `筛当前手机时间线`） | **整块缺失** |
| `本人私聊进展` | 微信进展摘要（`当前微信摘要引用`） | **是**（`取微信摘要快照` 内部调 `读库()`） | **空** |
| `相关剧情连续性` | SQLite `RQ_人物长期记忆` | 否 | **完整**（row_id 48／47／3） |

结论：**两个走 chat 变量＋锚签名的来源全丢，走数据库的来源完好。** 这正是签名误判的指纹；
如果是"没落盘"或"冷启动假清屏"，数据库那三条不会独善其身。

两个额外事实（原第四节没有覆盖，Codex 需要知道）：

1. **一次失配打掉两层记忆，不只是气泡不可见。**
   `取微信摘要快照`（`手机/摘要系统.ts:132`）用 `读库()` 重建摘要点，
   `当前微信摘要引用`（`:229`）再从快照取有效事件键。记录被过滤 → 摘要点为空 →
   `本人私聊进展` 也为空。所以玩家看到的不只是"聊天记录消失"，
   而是**角色对整段私聊历史彻底失忆**，同时数据库长期记忆还在——
   这会让 AI 写出"知道旧事、却不知道刚聊过什么"的分裂输出。
2. **日志里的模型输出证实了这一点。**
   沈静仪写的是"李梦阳，你刚才走得太匆忙了……我心里很不安"，
   完全依据状态包的情绪字段（`情绪:虚脱后怕`、`他一句话没说就走了`）编造，
   背后没有任何真实私聊支撑。角色在对一段她读不到的对话做反应。

这份日志同时说明：**玩家报的"上下文消失"和"聊天记录消失"是同一件事的两面**，
不需要再去找第二个根因。

## 五、已落地的修复

### 5.1 `src/人妻公寓/脚本/游戏逻辑/手机时间线租约.ts`

把原 `规范手机锚签名文本`（只归一 swipe_id 后做整串比较）替换为字段级比较：

- 新增 `解析手机锚签名(签名): unknown[] | null`：JSON 解析 + 校验为 6 元数组 + 归一 `[3]` swipe_id；
  形状未知返回 `null`。
- 新增常量 `手机锚签名字段数 = 6`、`手机锚签名正文位 = 1`。
- `手机锚消息签名匹配` 改为：
  1. 整串完全相等 → 匹配（快路径，行为不变）；
  2. 两侧都能解析成 6 元数组 → 除**正文位 `[1]`** 外的五个字段全部相等即视为同一分支；
  3. 任一侧形状未知（非对象锚、畸形 JSON）→ **失败关闭**，保持严格比较。
- `手机锚消息签名`（生成侧）**未改动**：仍写入完整六字段，保持与已发布旧档的双向兼容。

隔离强度未下降的理由（已写进代码注释）：
真实 swipe 会同时改 `swipe_id`；删楼后同楼重建会改 `send_date`；
身份变化会改 `is_user`/`name`/`force_avatar`；
删楼后同楼重建另有调用方的**对象引用比较**兜底（`手机时间线租约仍有效` 的 `当前锚消息 === 租约.锚消息引用`）。

### 5.2 `tests/人妻公寓/手机同楼分支隔离.test.mjs`

新增 4 个测试（原 5 个全部保留且通过）：

1. `宿主在同一分支内改写正文（宏展开/思维链剥离/楼层编辑）后微信仍属于当前分支`
   —— 三种真实改写场景，含带稳定键 `楼务:管理-0-下水堵塞-101` 的记录（对应玩家报的重复派发）。
2. `正文容差不放宽真实分支隔离：swipe、send_date、is_user、name、头像任一变化仍失配`
   —— 五个反例逐项断言仍然隔离。
3. `正文容差覆盖已发布旧档签名：swipe_id=null 与正文改写可同时发生`
   —— 旧档 `null` swipe_id 与正文改写叠加时应匹配；遇真实 swipe 仍隔离。
4. `签名形状未知时退回严格比较，不因容差放宽隔离`
   —— 非对象锚、畸形 JSON 两种失败关闭路径。
